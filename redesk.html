🎯 系统定位

替代 Notion 书架表单，建立自托管的私人书籍管理系统。将「书籍管理」「在线阅读」「阅读数据」「OPDS 推送」「数据备份」整合为单一 Docker 服务。


核心约束：

  • 单 Docker 容器 All-in-One，不拼接多个第三方组件
  • 使用人数 ≤ 5 人，轻量级 JWT 用户系统
  • EPUB 为主格式；TXT 上传自动转 EPUB；MOBI/PDF 仅存储/下载，不原生在线阅读
  • 元数据优先从 NeoDB 获取，中文书补全
  • 极其重视数据自主权：所有数据必须可随时导出

层级 选型 理由
后端 FastAPI (Python) 异步处理 IO 密集型任务（文件上传、NeoDB 抓取、EPUB 解析）；自动 Swagger 文档；AI 生成代码准确率最高；Python 的 zipfile / ebooklib / Pillow 生态处理 EPUB 最顺手
前端 React + Vite + Tailwind 极致简单，无框架约定负担；Vite 构建秒开；标准 React 组件，AI 辅助开发最成熟；React Router 声明式路由足够灵活；最终输出纯静态文件由 FastAPI 挂载
数据库 SQLite (WAL) 单文件零配置，5 人并发完全够用；备份就是复制一个文件；SQLAlchemy 未来可无缝迁移到 PostgreSQL
文件存储 本地文件系统 EPUB 和封面图直接存本地，读写无网络延迟；挂载宿主机目录持久化；不引入 OSS 避免网络依赖
在线阅读 epub.js Mozilla 出品，浏览器端 EPUB 渲染标准库；原生支持 CFI 定位、高亮、主题注入、目录导航；与 React 组件化封装成熟
部署 单 Docker + Uvicorn 运行时只有一个进程，没有 Node 运行时、没有进程管理器、没有多端口映射；镜像最小，维护最简
备份出口 rclone → Google Drive 增量同步，配置简单；数据自主权高；容器内 APScheduler 定时触发或宿主机 cron

开发模式 vs 生产模式

开发模式（本地）：

Terminal 1:  uvicorn main:app --reload --port 8000
Terminal 2:  cd frontend && npm run dev

# vite.config.js
proxy: { '/api': 'http://localhost:8000' }

# Browser: http://localhost:5173
# All /api/* auto-forwarded to FastAPI

生产模式（Docker）：

# Multi-stage build
FROM node:20-alpine AS frontend
COPY frontend/ . 
RUN npm ci && npm run build

FROM python:3.11-slim
COPY --from=frontend /app/dist ./static
COPY backend/ .
RUN pip install -r requirements.txt
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"]

# FastAPI mounts static files + SPA fallback
app.mount("/", StaticFiles(directory="static", html=True))

为什么不选 Next.js

❌ 不选 Next.js SSR（服务端渲染）
SSR 的核心价值是 SEO 和首屏速度。你的书库是私人系统，登录后才能访问，不需要 SEO；统计页面数据量极小，客户端 fetch 后渲染在 100ms 内完成，SSR 无感知收益。代价是容器内必须常驻 Node 进程 + Python 进程，镜像体积暴涨到 1GB+，违背单进程极简原则。
❌ 不选 Next.js API 路由
如果同时用 FastAPI 处理文件/数据库，又用 Next.js API 路由处理部分业务，会导致「双后端」架构混乱。Node 处理 EPUB 解析、封面提取、TXT 转换的库远不如 Python 成熟，数据库连接和异步模型也不如 Python 顺手。
⚠️ Next.js Static Export 可用，但没必要
Next.js 做 next export 输出纯静态文件，再由 FastAPI 挂载，这个路线是可行的。但相比 React + Vite：构建时间更慢（30-60s vs 3-5s）、输出体积更大、有框架约定负担。除非你有明确的 Shadcn/ui 或 Next 生态依赖，否则 Vite 更干净。

第三方服务定位

服务 推荐度 用途 不做什么
Cloudflare CDN ⭐⭐⭐⭐ 给 VPS 域名套 CDN，加速静态资源；HTTPS 证书自动 不存业务数据，不介入阅读逻辑
Cloudflare Tunnel ⭐⭐⭐⭐ Homelab 无公网 IP 时，直接获得 https 域名访问本地服务 不替代 Syncthing，只做访问入口
阿里云 OSS ⭐⭐ 仅当 VPS 磁盘 < 50GB 且书库增长极快时，冷存历史文件 不做主力存储，避免上传/下载走网络增加复杂度
Google Drive ⭐⭐⭐⭐ rclone 定时增量同步：数据库 + 书库文件 + Markdown 笔记 不做实时同步，做定时冷备
Syncthing ⭐⭐⭐⭐ Homelab ↔ VPS 双向实时同步，任何一边挂掉另一边有完整数据 不做公网访问，只做数据冗余

原则：第三方服务只解决「怎么访问」和「怎么备份」，不介入「怎么存书、怎么阅读、怎么记笔记」的核心业务逻辑。即使所有第三方服务同时挂掉，你的单 Docker 容器依然可以在本地正常运行。

🧩 模块设计（全局规划）

系统拆分为 6 个顶层模块，按「书籍生命周期」和「阅读数据流」组织。模块间通过 FastAPI 路由和数据库关系耦合，不引入消息队列等中间件。

模块 1：基础架构

职责：部署、进程、数据库、认证、配置、全局 UI

单 Docker 容器内维持一个 Uvicorn 进程；SQLite 以 WAL 模式运行，数据文件挂载宿主机；JWT 用户系统隔离多用户数据；环境变量通过 Pydantic BaseSettings 统一管理；前端 React 构建产物由 FastAPI StaticFiles 挂载，实现 SPA fallback。

核心表：users | 外部依赖：无

模块 2：书籍管理

职责：书籍全生命周期 — 录入、元数据、状态流转、文件上传、封面、批量操作

提供书籍 CRUD 接口；集成 NeoDB API 自动抓取中文元数据；支持粘贴 URL 预填和 AI 辅助文本解析；定义「想读/待收录/已收录/在读/已读」状态机；上传 EPUB 后自动提取封面、更新状态；文件按 {book_id}/ 目录组织；支持批量改状态/标签/删除；回收站软删除；书架卡片展示「上次读到」位置。

核心表：books, tags, book_tags, status_history | 外部依赖：NeoDB API, 可选 LLM API

模块 3：在线阅读器

职责：浏览器 EPUB 渲染、阅读交互、主题、进度、TTS

基于 epub.js 封装 React 阅读器组件；支持目录导航、书签（CFI）、阅读进度百分比/物理页码、阅读计时、主题与字体切换、快捷键、专注模式、移动端快读模式；markClicked 事件支持点击高亮查看批注；TTS 接入第三方 AI 语音 API（讯飞/Mimo），按段落调用音频流。

核心表：bookmarks, reading_sessions | 外部依赖：可选 TTS API

模块 4：阅读数据

职责：阅读行为产生的所有数据 — 主动笔记、自动统计、目标、导出

epub.js 高亮层与后端数据分离：前端画高亮，后端存 CFI + 文本 + 批注；快捷标签（💡❓⭐📌）支持后期筛选；独立笔记与书籍关联；笔记列表支持按书/按时间查看并跳转回阅读位置；笔记全文搜索；自动异步备份为 Markdown；阅读时长聚合、热力图、趋势图、已读/未读比例、类别分布；年度阅读目标 + 进度环；阅读 Streak 连续天数；今日随机推荐。

核心表：highlights, notes, reading_sessions, reading_goals | 外部依赖：无

模块 5：OPDS 服务

职责：第三方阅读器订阅协议

输出标准 OPDS 1.2 Atom XML；支持按收录状态、标签筛选；提供搜索接口和书籍下载链接；KOReader、Librera 等可通过订阅地址直接浏览书库并下载阅读。不处理阅读进度回传。

核心表：复用 books, tags | 外部依赖：无

模块 6：备份与导出

职责：数据库备份、文件同步、一键导出、跨节点冗余

APScheduler 定时备份 SQLite 数据库（保留最近 N 份）；rclone 增量同步书库文件到 Google Drive；手动一键打包导出全部数据（ZIP：JSON + Markdown + 原文件）；可选 Syncthing 实现 Homelab ↔ VPS 双向实时同步。

核心表：无 | 外部依赖：rclone, Google Drive API, 可选 Syncthing

设计原则：所有模块共享同一个 SQLite 数据库，通过 SQL 关系（外键、JOIN）实现数据关联，不引入 Redis/RabbitMQ 等中间件。文件系统作为「第二数据库」存储 epub/封面/笔记 Markdown，与 SQLite 记录通过 file_path 关联。

🗺️ 开发路线图

第一期 核心闭环（MVP）

目标：让用户能完成「录入 → 上传 → 阅读 → 记笔记 → 导出」的最小闭环。系统可自用，但体验较朴素。

  • 1
    基础架构：单 Docker 部署、SQLite、JWT 用户登录、暗色模式、空状态提示
  • 2
    书籍管理：手动录入、NeoDB 抓取、URL 预填、封面自动提取、标签、搜索排序、状态字段、上传 EPUB 自动改状态、文件存储、回收站
  • 3
    在线阅读器：epub.js 基础渲染、目录、书签、位置恢复、进度百分比、主题切换、暗色/护眼、快捷键
  • 4
    阅读数据：划线高亮、高亮批注、独立笔记、笔记列表、编辑删除
  • 5
    备份导出：SQLite 自动备份、手动一键导出（JSON + Markdown + 文件）

本期不做：AI 辅助录入、TTS、物理页码、markClicked、OPDS、统计看板、批量导入导出、TXT/MOBI/PDF 支持、阅读计时、阅读热力图、阅读目标。

第二期 满足日常使用

目标：补齐格式兼容、多端访问、自动化备份，让系统成为日常主力工具。

  • 1
    格式兼容：TXT 上传自动转 EPUB；MOBI/AZW3/PDF 仅存储+下载（提取元数据，不入阅读器）
  • 2
    OPDS 服务：基础协议、按状态/标签筛选、搜索、下载链接（支持 KOReader/Librera）
  • 3
    批量操作：批量导入（CSV/JSON）、批量导出、批量改状态/标签、重复检测（模糊匹配）
  • 4
    阅读数据增强：阅读时长统计、已读/未读比例、类别分布、书架总量、个人档案页
  • 5
    备份自动化：rclone 定时同步 Google Drive；本地与 VPS Syncthing 双向同步
  • 6
    笔记增强：笔记全文搜索、导入外部笔记（Notion/Obsidian）模糊匹配、笔记自动备份 Markdown

第三期 体验丰富

目标：打磨细节，提升阅读和管理体验，让系统用起来「爽」。

  • 1
    阅读器增强：物理页码生成（"第 X 页"）、markClicked 点击高亮查看批注、移动端快读模式、专注模式、字体自定义上传
  • 2
    快捷批注：高亮时 💡❓⭐📌 预设标签、按标签筛选笔记
  • 3
    阅读数据深化：阅读计时（本次/累计）、阅读进度预估剩余时间、阅读热力图、阅读 Streak、年度目标、今日推荐
  • 4
    管理体验：书架「上次读到」直接展示、批量改状态、"想要 vs 实际"对比、随机推荐
  • 5
    AI 辅助录入：粘贴豆瓣文本 → LLM 解析 → 自动回填表单
  • 6
    TTS 语音朗读：接入讯飞/Mimo 等第三方 AI TTS，段落级朗读

第四期 后期拓展

目标：引入 AI 能力，探索更智能的阅读辅助，保持架构可扩展。

  • 1
    AI 笔记分析（扩展模块）：按 💡❓⭐📌 标签分组 → LLM 归纳章节摘要、核心观点、个人启发；生成可编辑的 AI 笔记
  • 2
    AI 阅读助手：针对单本书问答（基于划线内容）、关键词提取、自动目录补全
  • 3
    社交化（可选）：5 人内简单评论、书籍分享链接、借阅管理（如有实体书）
  • 4
    性能优化：SQLite → PostgreSQL 迁移、全文搜索升级 Meilisearch、EPUB 全文索引
  • 5
    客户端探索：Tauri 桌面端、PWA 离线缓存、阅读器手势增强

扩展模块原则：AI 能力以「插件」形式设计，LLM API 调用集中在独立 service 层，不耦合到核心 CRUD 逻辑。即使 AI 服务不可用，系统基础功能不受影响。
