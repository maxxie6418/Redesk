# 阅读资产整理与话题工作区细化计划

更新日期：2026-07-06

## 1. 背景

当前 Redesk 已经完成书架与文件管理、阅读器与笔记沉淀、话题阅读基础闭环。系统已经可以完成以下主链路：

1. 上传或创建书籍。
2. 管理书籍文件、元数据、分类、标签与状态。
3. 打开 EPUB 阅读并生成进度、高亮、附注、独立笔记、书签。
4. 将书籍、高亮、笔记、章节片段加入话题。
5. 在话题工作区内维护问题、判断、比较等沉淀内容。

本计划聚焦四个可以继续细化的功能方向：

1. 文件到书籍的自动归档体验。
2. 回看路径优化。
3. 话题内分层。
4. 话题时间线。

这四项不是彼此孤立的新功能，而是围绕“收集 → 整理 → 阅读 → 沉淀 → 回看 → 再组织”的使用闭环继续加厚体验。

## 2. 目标与原则

### 2.1 总目标

把当前已经可用的阅读资产链路，从“能完成操作”推进到“能自然整理、快速回看、持续复用”。

### 2.2 设计原则

1. 不破坏现有核心建模：书籍仍是原始资产入口，话题仍只引用阅读痕迹，不占有原始高亮、笔记和书籍。
2. 不做静默高风险自动化：文件匹配、归档、话题引用等动作可以推荐，但关键落账必须由用户确认。
3. 优先复用现有表与接口：能通过组合现有 `book_files`、`books`、`highlights`、`notes`、`bookmarks`、`topics`、`topic_*` 表完成的，不优先新增复杂结构。
4. 让 AI 保持后置增强：本计划先完成无 AI 的确定性体验；AI 可以作为后续推荐、总结、聚类能力接入，但不作为首版依赖。
5. 所有可回看的内容必须能回到原始上下文：高亮、笔记、书签、章节片段、话题事件都应尽量能回到书籍、阅读位置或来源对象。

## 3. 功能一：文件到书籍的自动归档体验

### 3.1 用户问题

用户批量上传 EPUB/PDF 等文件后，当前系统虽然已经有未关联文件池和匹配接口，但用户仍容易遇到这些问题：

1. 上传完成后不知道下一步是否应该立刻处理。
2. 未关联文件与书籍条目之间的匹配仍需要较多人工判断。
3. 文件名、EPUB 内元数据、已有书籍元数据之间的关系没有被充分展示。
4. 高置信匹配和低置信匹配没有形成清晰的批量处理路径。
5. 文件处理完以后，用户缺少“归档完成”的反馈。

### 3.2 推荐形态

将“未关联文件处理”升级为“文件归档工作台”。

入口包括：

1. 批量上传完成后的下一步入口。
2. 文件库中的“处理未关联文件”。
3. 书籍详情页中的“查找可关联文件”。

工作台围绕文件行展开，每一行展示：

| 信息 | 说明 |
| --- | --- |
| 文件名 | 原始文件名与标准化后的候选书名 |
| 文件特征 | 格式、大小、checksum、EPUB title、creator、publisher、identifier |
| 推荐书籍 | 系统按置信度排序后的候选书籍 |
| 推荐依据 | 如书名完全命中、作者命中、ISBN 命中、文件名前缀命中 |
| 推荐动作 | 关联到已有书籍、新建书籍、跳过、标记为暂不处理 |
| 风险提示 | 同名多书、同书多版本、文件重复、目标书已有主文件 |

### 3.3 功能拆分

#### A. 候选生成

后端统一生成候选，前端只展示和提交确认。

候选信号分层：

1. checksum 去重：判断文件是否已存在。
2. EPUB 元数据：优先使用 `dc:title`、`dc:creator`、`dc:identifier`。
3. 文件名标准化：去站点后缀、格式噪音、括号噪音、版本噪音。
4. 书名匹配：完整包含、前缀命中、关键词覆盖、模糊相似度。
5. 作者匹配：中文名、外文名、括号内作者名的弱匹配。
6. ISBN 或 identifier 匹配：作为最高置信信号之一。

候选返回应包含：

- `file_id`
- `parsed_metadata`
- `candidates[]`
- `confidence`
- `reasons[]`
- `warnings[]`
- `recommended_action`

#### B. 批量确认

工作台顶部提供批量动作：

1. 应用全部高置信推荐。
2. 只看需要人工确认的文件。
3. 批量跳过低置信文件。
4. 批量新建书籍草稿。
5. 退出并保留未处理状态。

批量应用时仍应逐条校验：

- 文件是否仍未关联。
- 目标书是否属于当前用户。
- 目标书是否在回收站。
- 是否会造成主文件冲突。
- 是否命中重复 checksum。

#### C. 新建书籍草稿

当没有候选书籍时，允许从文件特征生成新书草稿：

- 书名来自 EPUB title 或标准化文件名。
- 作者来自 EPUB creator 或文件名推断。
- ISBN、出版社、语言等字段能取则取。
- 文件自动作为该书的关联文件。
- 如果是 EPUB，可继续复用现有封面抽取能力。

首版不建议“自动直接建书”，而是展示草稿并由用户确认。

#### D. 归档完成反馈

工作台完成后给出归档结果摘要：

- 已关联到已有书籍数量。
- 已创建新书数量。
- 已跳过数量。
- 仍需人工处理数量。
- 重复文件数量。

### 3.4 数据与接口影响

优先复用已有能力：

- `book_files.book_id` 支持 null，已可表达未关联文件池。
- `POST /files/match/candidates` 已定义批量候选生成方向。
- `POST /files/match/apply-batch` 已定义批量应用方向。
- `POST /files/{fileId}/match` 可保留为单文件补救接口。

可能需要补充的接口能力：

1. 候选接口返回更细的 `reasons` 与 `warnings`。
2. 批量应用接口支持多种动作：关联已有书、新建书并关联、跳过。
3. 文件库列表支持按“归档状态”筛选：未关联、已关联、重复疑似、需确认。

首版不强制新增表。若后续需要持久化“跳过 / 暂不处理 / 已确认低置信”的状态，可考虑在 `book_files` 增加轻量字段，或用扩展事件表记录处理状态。

### 3.5 验收标准

1. 批量上传完成后，用户能直接进入本批文件的归档工作台。
2. 工作台能一次展示多个文件的推荐候选、置信度、推荐依据和风险提示。
3. 用户可以批量应用高置信推荐，也可以逐条修正。
4. 无匹配书籍时，可以从文件信息创建书籍草稿并关联文件。
5. 不发生静默误绑定；所有归档落账都由用户确认。
6. 归档结束后，用户能看到处理结果摘要。

## 4. 功能二：回看路径优化

### 4.1 用户问题

当前系统已经有高亮、笔记、书签、阅读进度、阅读笔记汇总页和跳回原文能力，但用户真实回看时不一定只按“书籍”回看，常见路径包括：

1. 最近几天我标了什么。
2. 某本书里我当时觉得重要的内容是什么。
3. 所有“疑问”类标记在哪里。
4. 某个话题里新增了哪些阅读痕迹。
5. 我上次读到哪里、为什么停下。
6. 我想从一条笔记回到原文上下文继续读。

因此需要把“能搜索”进一步细化为“有清晰的回看入口”。

### 4.2 推荐形态

新增或改造为“回看中心”，并在书籍详情、阅读器、话题工作区中提供局部回看入口。

回看中心可以包含四类视图：

| 视图 | 目标 |
| --- | --- |
| 最近痕迹 | 按时间查看最近新增或编辑的高亮、笔记、书签、话题沉淀 |
| 按书回看 | 以书为单位查看高亮、笔记、书签、阅读进度和最近阅读时间 |
| 按标记回看 | 按重要、疑问、启发等 `mark_type` 聚合 |
| 按话题回看 | 查看某个话题下最近新增的书籍、痕迹、沉淀内容 |

### 4.3 功能拆分

#### A. 最近痕迹流

聚合以下对象：

- 高亮。
- 独立笔记。
- 书签。
- 话题沉淀内容。
- 阅读进度更新。

每条记录显示：

- 类型。
- 所属书籍或话题。
- 内容摘要。
- 创建或更新时间。
- 标记类型。
- 操作入口：跳回原文、加入话题、复制、导出。

#### B. 单书回看路径

书籍详情页增加“阅读痕迹”区块：

1. 最近阅读位置。
2. 高亮数量、笔记数量、书签数量。
3. 最近 5 条高亮/笔记。
4. 按标记类型筛选。
5. 跳转到完整单书痕迹页。

阅读器内增加“本书回看抽屉”：

1. 本书目录。
2. 本书书签。
3. 本书高亮。
4. 本书笔记。
5. 当前章节相关痕迹。

#### C. 标记回看

围绕 `mark_type` 做聚合视图：

- 重要。
- 疑问。
- 启发。
- 未标记。

每种标记下支持：

- 按书筛选。
- 按话题筛选。
- 按时间排序。
- 批量加入话题。

#### D. 回到原文增强

现有跳回原文能力继续保留，并增加失败兜底：

1. CFI 可用时直接定位。
2. CFI 失效时，尝试按原文片段搜索。
3. 搜索仍失败时，打开书籍并提示用户手动查找。
4. 对每次失败给出可理解提示，不静默失败。

### 4.4 数据与接口影响

优先复用：

- `highlights`、`notes`、`bookmarks`、`reading_progress`。
- `GET /highlights`、`GET /notes`、搜索接口和最近阅读接口。
- 话题详情与话题痕迹汇总接口。

可能需要补充：

1. `GET /review/recent`：聚合最近痕迹流。
2. `GET /books/{id}/review`：单书回看摘要。
3. `GET /review/by-mark-type`：按标记聚合。
4. 现有 `GET /overview` 可只保留概览统计，不建议继续把所有回看逻辑塞入 overview。

### 4.5 验收标准

1. 用户可以从一个统一入口看到最近阅读痕迹。
2. 用户可以从书籍详情快速回看本书高亮、笔记、书签和进度。
3. 用户可以按标记类型找到所有疑问、重要、启发类内容。
4. 用户可以从任一高亮或笔记尽量跳回原文。
5. 跳回失败时有明确提示和兜底路径。

## 5. 功能三：话题内分层

### 5.1 用户问题

当前话题已经能关联书籍、高亮、笔记、章节片段和沉淀内容，但随着材料增多，话题工作区容易变成“所有东西混在一起”的聚合页。

用户在话题内真实需要的是分层处理：

1. 哪些是原始资料。
2. 哪些是阅读痕迹。
3. 哪些是我自己的阶段性判断。
4. 哪些内容还需要整理。
5. 哪些内容已经可以输出。

### 5.2 推荐形态

将话题工作区分为四层：

| 层级 | 内容 | 作用 |
| --- | --- | --- |
| 资料层 | 关联书籍、章节片段、后续扩展的外部来源 | 表示话题材料来源 |
| 痕迹层 | 高亮、笔记、书签、摘录 | 表示从阅读中收集到的证据与灵感 |
| 思考层 | 问题、判断、比较 | 表示用户自己的整理与推理 |
| 输出层 | 摘要、提纲、草稿、结论 | 表示可复用成果 |

首版可以先实现 UI 分层与筛选，不必一次性引入复杂新表。

### 5.3 功能拆分

#### A. 工作区导航分层

话题详情页提供层级导航：

1. 总览。
2. 资料。
3. 痕迹。
4. 思考。
5. 输出。
6. 时间线。

总览页显示每层摘要：

- 资料数量。
- 高亮数量。
- 笔记数量。
- 章节片段数量。
- 问题数量。
- 判断数量。
- 比较数量。
- 最近活动。

#### B. 资料层

包含：

- 已关联书籍。
- 章节片段。
- 未来可扩展的外部链接或文件。

操作：

- 添加书籍。
- 移除书籍引用。
- 打开书籍详情。
- 从书籍进入阅读。
- 查看该书贡献了多少高亮、笔记、片段。

#### C. 痕迹层

包含：

- 高亮。
- 笔记。
- 书签。
- 章节片段。

操作：

- 按书筛选。
- 按标记类型筛选。
- 跳回原文。
- 引用到思考层。
- 从话题移除引用。

#### D. 思考层

复用当前 `topic_entries` 的 entry_type：

- QUESTION。
- JUDGMENT。
- COMPARISON。

增强方向：

1. 每条思考可以关联来源痕迹。
2. 每条思考有状态：草稿、待补证、已确认。
3. 可按类型筛选。
4. 可从高亮/笔记快速生成一条思考。

首版如不改表，可先把来源引用保存在 entry 内容结构或前端操作上下文中；正式实现更建议补充思考与痕迹之间的引用关系表。

#### E. 输出层

输出层用于保存更成型的内容：

- 话题摘要。
- 文章提纲。
- 阶段结论。
- 读书报告草稿。

首版建议先以 `topic_entries.entry_type` 新增或扩展一种输出类型承载；如果不希望变更枚举，可以先作为话题说明或独立 Markdown 草稿能力后置。

### 5.4 数据与接口影响

优先复用：

- `topic_books`
- `topic_highlights`
- `topic_notes`
- `topic_segments`
- `topic_entries`

可能新增或调整：

1. `topic_entries.entry_type` 是否扩展 `OUTPUT`。
2. 是否新增 `topic_entry_sources`，表达某条问题、判断、比较引用了哪些高亮、笔记或片段。
3. 话题详情接口增加按层级返回的聚合结构。
4. 话题痕迹接口支持 `layer`、`book_id`、`mark_type`、`entry_type` 筛选。

首版建议：先不新增复杂表，仅完成工作区分层、筛选、统计和现有数据的分区展示。

### 5.5 验收标准

1. 话题工作区不再把所有内容混排，而是能按资料、痕迹、思考、输出分区查看。
2. 用户能快速看出一个话题有哪些书、哪些阅读痕迹、哪些自己的判断。
3. 用户能从痕迹层跳回原文，也能把痕迹转为思考层条目。
4. 删除话题仍然只软删除话题，不影响原始书籍、高亮和笔记。
5. 移除话题引用不会删除原始阅读痕迹。

## 6. 功能四：话题时间线

### 6.1 用户问题

话题不是静态文件夹，而是一个持续演化的阅读与思考项目。用户需要知道：

1. 这个话题是何时开始的。
2. 哪些书什么时候加入。
3. 哪些高亮、笔记、判断推动了话题变化。
4. 最近话题有什么新增内容。
5. 一个阶段性结论是基于哪些历史材料形成的。

### 6.2 推荐形态

在话题工作区增加“时间线”视图，按时间展示话题内发生的重要事件。

事件类型包括：

| 事件类型 | 来源 |
| --- | --- |
| 创建话题 | `topics.created_at` |
| 编辑话题 | `topics.updated_at` |
| 加入书籍 | `topic_books.created_at` |
| 加入高亮 | `topic_highlights.created_at` |
| 加入笔记 | `topic_notes.created_at` |
| 加入章节片段 | `topic_segments.created_at` |
| 新建沉淀 | `topic_entries.created_at` |
| 编辑沉淀 | `topic_entries.updated_at` |
| 移除引用 | 首版可不显示；如需显示，需要事件日志 |

### 6.3 功能拆分

#### A. 派生时间线

首版不新增事件表，直接从现有表的 `created_at`、`updated_at` 派生时间线。

优点：

- 不增加写入复杂度。
- 能快速展示大部分正向事件。
- 与现有数据兼容。

局限：

- 无法展示删除或移除引用的历史。
- 无法展示字段级修改细节。
- `updated_at` 只能表示最近一次修改。

#### B. 时间线展示

每条事件显示：

- 时间。
- 事件类型。
- 事件主体。
- 来源书籍。
- 内容摘要。
- 可执行动作。

可执行动作包括：

- 打开书籍。
- 跳回原文。
- 查看沉淀条目。
- 从时间线进入对应层级。

#### C. 筛选与分组

支持：

1. 按事件类型筛选。
2. 按书籍筛选。
3. 按时间范围筛选。
4. 按天、周、月分组。
5. 只看最近新增。

#### D. 事件日志增强

如果后续希望看到完整历史，可以新增 `topic_events` 表。

建议字段：

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| topic_id | 话题 |
| owner_id | 归属用户 |
| event_type | 事件类型 |
| subject_type | book / highlight / note / segment / entry / topic |
| subject_id | 来源对象 ID |
| action | created / updated / linked / unlinked / deleted |
| payload | JSON 快照或摘要 |
| created_at | 事件时间 |

但首版不建议立即上事件日志，除非明确需要审计级历史。

### 6.4 数据与接口影响

首版建议新增：

- `GET /topics/{id}/timeline`

该接口从现有话题聚合数据派生返回：

- `events[]`
- `event_type`
- `subject_type`
- `subject_id`
- `title`
- `summary`
- `book_id`
- `cfi`
- `created_at`

不建议前端在多个接口间自行拼装时间线，因为排序、owner 校验和隐藏软删除数据更适合由后端统一处理。

### 6.5 验收标准

1. 用户可以在话题内看到按时间排列的书籍、痕迹、片段和沉淀新增记录。
2. 时间线事件可以跳到对应书籍、原文或工作区层级。
3. 时间线默认不显示已软删除或无权限访问的内容。
4. 首版即使不记录移除历史，也要在文档中明确这是派生时间线，不是完整审计日志。

## 7. 推荐实施顺序

### 阶段 A：文件归档工作台

优先原因：

- 直接改善书库建库体验。
- 已有未关联文件池、匹配候选和批量应用接口方向。
- 与阅读器和话题复杂度相对解耦。

执行项：

1. 完善后端候选生成规则与返回结构。
2. 完善批量应用接口，支持关联已有书和新建书草稿。
3. 前端新增文件归档工作台。
4. 批量上传完成后接入归档入口。
5. 文件库接入同一个工作台。
6. 补充重复文件、主文件冲突、低置信候选提示。

### 阶段 B：回看路径优化

状态：已开始落地。当前已完成 `GET /books/{id}/review` 单书回看摘要、书籍详情阅读留痕区的书签计数与最近回看入口；全局回看中心、按标记类型聚合和阅读器内本书回看抽屉仍待后续继续。

优先原因：

- M2 阅读痕迹已闭环，下一步应提升再利用效率。
- 回看能力也是话题分层和时间线的基础。

执行项：

1. 设计最近痕迹聚合接口。
2. 书籍详情增加阅读痕迹摘要。
3. 阅读笔记页或新增回看中心支持最近、按书、按标记类型视图。
4. 阅读器内增加本书回看抽屉或强化现有侧栏。
5. 强化跳回原文失败兜底。

### 阶段 C：话题内分层

优先原因：

- 当前话题已经可用，但材料变多后需要结构化。
- 分层后，话题时间线和未来 AI 整理都会更清晰。

执行项：

1. 改造话题工作区导航结构。
2. 将现有书籍、高亮、笔记、片段、entry 映射到资料、痕迹、思考层。
3. 增加层级统计。
4. 支持痕迹层筛选与跳回原文。
5. 支持从痕迹生成思考条目。
6. 评估是否需要 `OUTPUT` 类型或独立输出草稿能力。

### 阶段 D：话题时间线

状态：基础版已落地。当前已完成 `GET /topics/{id}/timeline` 派生时间线接口，并在话题工作区右侧展示最近时间线事件；事件筛选、分组、跳转到工作区层级和完整事件日志仍待后续继续。

优先原因：

- 时间线依赖话题数据已经较稳定。
- 更适合在分层之后落地，否则时间线事件缺少清晰归属。

执行项：

1. 新增后端时间线派生接口。
2. 前端增加话题时间线视图。
3. 支持事件类型、书籍、时间范围筛选。
4. 支持事件跳转到对应层级或原文。
5. 在文档中明确首版是派生时间线，不是审计日志。

## 8. 优先级建议

### P0

1. 文件归档工作台的候选展示与批量确认。
2. 批量上传完成后的“继续归档这些文件”入口。
3. 单书阅读痕迹摘要与跳回原文兜底。
4. 话题工作区资料层、痕迹层、思考层的基础分层。

### P1

1. 从文件信息新建书籍草稿。
2. 回看中心的最近痕迹流。
3. 按标记类型回看。
4. 话题时间线派生接口与基础视图。
5. 从话题痕迹生成思考条目。

### P2

1. 话题输出层。
2. `topic_entry_sources` 引用关系。
3. `topic_events` 完整事件日志。
4. AI 辅助文件归档、痕迹聚类、话题总结和证据整理。

## 9. 不做范围

本计划首轮不包含：

1. AI 自动静默归档文件。
2. AI 自动生成话题结论并写入用户笔记。
3. 多人协作、评论、权限流转。
4. 完整审计日志。
5. 外部网页剪藏或外部文献管理器同步。
6. 对 PDF 阅读器做深度改造。
7. 移动端专项适配。

## 10. 风险与注意事项

### 10.1 文件误绑定风险

文件归档推荐必须可解释、可撤销。不应为了减少点击而默认静默绑定。

### 10.2 话题数据污染风险

话题仍然只引用原始痕迹。任何“移出话题”都不得删除原始高亮、笔记、书籍或文件。

### 10.3 回看入口过多风险

回看中心、阅读器侧栏、书籍详情、话题工作区都可能出现回看入口。需要统一概念：

- 全局回看：看最近与跨书。
- 单书回看：看一本书。
- 话题回看：看一个话题。
- 阅读器回看：辅助当前阅读。

### 10.4 时间线语义风险

首版派生时间线不是完整历史。它展示“当前仍存在的数据对象的创建或更新时间”，不保证还原所有删除、移除、编辑历史。

## 11. 完成标志

当以下流程可以顺畅完成时，可认为本轮功能细化达成：

1. 用户批量上传一批 EPUB 后，可以在同一上下文进入文件归档工作台。
2. 用户能看到每个文件推荐匹配哪本书、为什么推荐，并批量确认高置信结果。
3. 用户能从书籍详情或回看中心找到最近高亮、笔记、书签，并跳回原文。
4. 用户进入一个话题后，可以按资料、痕迹、思考分层查看内容。
5. 用户能在话题内看到材料加入与沉淀产生的时间线。
6. 全流程不依赖 AI，也不破坏“话题只引用、不占有阅读痕迹”的核心原则。

## 12. 后续可讨论问题

1. 文件归档中的“跳过”是否需要持久化状态。
2. 是否需要允许用户手动调整匹配规则权重。
3. 回看中心是独立一级导航，还是并入阅读笔记页。
4. 话题输出层首版是复用 `topic_entries`，还是新增独立草稿模型。
5. 是否需要 `topic_entry_sources` 来表达判断与证据之间的关系。
6. 话题时间线是否需要在第二阶段升级为完整事件日志。
7. AI 应优先接入哪个环节：文件归档、回看聚类、话题整理，还是输出层草稿。
