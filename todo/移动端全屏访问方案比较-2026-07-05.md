# Redesk 移动端全屏访问方案比较
更新日期：2026-07-05

## 1. 背景

当前诉求不是把 Redesk 重做成完整的原生移动应用，而是解决“手机浏览器访问时，浏览器自身按钮干扰操作，希望尽量全屏使用”的问题。

基于当前仓库实现，Redesk 仍是典型的 Web 架构：

- 前端：Vite + React + TypeScript
- 后端：Fastify
- 阅读器：`epub.js`
- 数据库：SQLite（`better-sqlite3`）
- 文件与备份：依赖服务端本地文件系统与 SQLite 文件

因此，移动端方案应分成两类看待：

1. `PWA`：继续沿用现有 Web 架构，只改善手机端启动与全屏体验
2. `原生安卓打包`：把前端封装为 APK，必要时再接入少量原生能力

本说明只比较这两条路线，不把“完全离线、本地数据库、自带服务端”的重度移动化迁移纳入当前范围。

## 2. 结论先行

对于当前诉求，推荐顺序如下：

1. 先做 `PWA`
2. 如果 PWA 在目标手机浏览器上仍不够干净，再做“原生安卓壳 APK”

原因：

- 当前问题的根因是“浏览器外壳干扰”，不是“缺少原生能力”
- PWA 改造成本最低，且不需要迁移后端
- 原生安卓壳能进一步稳定全屏体验，但构建链、签名、调试成本更高
- 两条路线都不要求现在重写 Redesk 的后端、SQLite、文件存储或阅读器逻辑

## 3. 方案一：PWA

### 3.1 适用目标

- 在手机上以接近独立 App 的方式打开 Redesk
- 尽量隐藏浏览器地址栏、底部工具栏、返回/分享等浏览器 UI 干扰
- 继续连接现有 Redesk 服务端

### 3.2 前置环境

- 现有前端构建环境可正常使用
  - Node.js 22
  - pnpm
  - Vite 构建链
- 一个可被手机访问的 Redesk 地址
- 更推荐使用 `HTTPS`
  - 正式安装与稳定体验最好基于 HTTPS
  - 局域网临时测试可先试，但安装与缓存能力可能受浏览器限制
- 一套 App 图标资源

### 3.3 需要改造的内容

- 增加 `manifest.webmanifest`
- 配置应用名、图标、启动模式、主题色、背景色
- 增加移动端启动相关 meta
- 增加基础 `service worker`
- 明确缓存策略
  - App Shell 可缓存
  - API 数据不做激进离线缓存
  - EPUB 下载流与大文件缓存要谨慎
- 增加“安装到主屏幕”的引导
- 在手机上验证启动后是否以独立应用模式显示

### 3.4 优点

- 成本最低
- 不改变现有前后端职责
- 不需要 Android Studio、JDK、签名等原生环境
- 可先快速验证“全屏是否已经够用”

### 3.5 局限

- 仍然是 Web 应用，不是原生 App
- 不同安卓浏览器对“全屏沉浸”的支持程度不完全一致
- 某些浏览器即使安装为 PWA，仍可能保留少量系统或浏览器痕迹
- 对文件系统、通知、后台任务等高级能力不如原生壳稳定

### 3.6 预估工作量

- 最小可用版本：`0.5 ~ 2 天`
- 若再补安装引导、缓存细化、图标与启动体验优化：`2 ~ 4 天`

### 3.7 风险点

- HTTPS 未就位时，正式体验可能不稳定
- `epub.js` 相关文件流在移动端需要实机验证
- 大文件缓存策略处理不当，可能带来存储占用或版本更新不及时问题

## 4. 方案二：原生安卓打包

### 4.1 适用目标

- 希望以 APK 形式安装
- 希望更稳定地全屏显示，避免浏览器 UI 干扰
- 仍然主要连接现有 Redesk 服务端，而不是把整个后端搬到手机里

### 4.2 推荐实现方式

当前最合理的做法不是重写原生页面，而是：

- 保留现有 Web 前端
- 使用安卓壳方案（如 Capacitor）封装为 APK
- 继续请求现有 Fastify API
- 后续按需接入少量原生能力

这条路线本质上是“给现有 Web 应用套一个原生容器”，而不是“把项目迁移成原生安卓架构”。

### 4.3 前置环境

- Node.js 22
- pnpm
- Android Studio
- JDK 17
- Android SDK
- 模拟器或真机调试环境
- APK 签名所需 keystore
- 一个可访问的 Redesk 服务地址，最好为 `HTTPS`

### 4.4 需要改造的内容

- 引入安卓壳工程
- 配置 Web 资源打包到壳内
- 配置网络访问域名与安全策略
- 验证登录态
  - 当前系统使用 cookie/session
  - 需要重点验证 WebView 下的会话行为
- 验证阅读器页面
  - `epub.js`
  - 文件流下载
  - `Range` 请求
- 验证上传、下载、导出、备份等移动端交互
- 处理状态栏、沉浸式、横竖屏与安全区域

### 4.5 优点

- 全屏体验通常比 PWA 更稳定
- 能真正以 APK 安装与分发
- 后续若要接入原生分享、文件选择、通知等能力，扩展空间更大

### 4.6 局限

- 构建链更重
- 需要维护安卓工程
- 调试成本明显高于 PWA
- 仍然没有解决“服务端依赖”问题
  - 只是把前端装进 APK
  - 后端、SQLite、文件、备份逻辑仍在服务器端

### 4.7 预估工作量

- 最小可用版本：`3 ~ 7 天`
- 若补齐登录态、阅读器、下载上传、导出备份、沉浸式适配与真机兼容性：`1 ~ 3 周`

### 4.8 风险点

- WebView 下 cookie/session 行为需要专项验证
- 阅读器文件流与 `Range` 支持是关键风险点
- 各品牌安卓机在 WebView、文件权限、外链打开行为上差异较大

## 5. 两个方案的差异汇总

| 维度 | PWA | 原生安卓打包 |
| --- | --- | --- |
| 目标 | 解决浏览器 UI 干扰，接近全屏 | 稳定全屏，并提供 APK 安装 |
| 是否要 Android 原生环境 | 否 | 是 |
| 是否要改后端 | 否 | 否 |
| 是否要迁移数据库/文件系统 | 否 | 否 |
| 改造成本 | 低 | 中 |
| 调试成本 | 低 | 中到高 |
| 全屏稳定性 | 中 | 高 |
| 分发方式 | 浏览器安装到主屏幕 | 直接安装 APK |
| 推荐优先级 | 高 | 中 |

## 6. 对 Redesk 当前状态的判断

当前 Redesk 更适合先走 `PWA`，不适合直接把“原生安卓打包”当成第一步，原因如下：

- 项目主体仍是 Web 管理系统 + Web 阅读器
- 后端承担了文件、数据库、备份、导出、会话、下载流等关键职责
- 当前移动端目标只是“更干净地全屏使用”，并不需要原生专属能力
- PWA 已足以验证真实需求：如果 PWA 安装后体验已经足够，就没有必要立即承担安卓工程维护成本

## 7. 推荐实施顺序

### 7.1 第一阶段：PWA 最小落地

目标：

- 手机桌面可安装
- 启动后尽量以独立应用样式显示
- 不影响现有桌面端与服务端部署

验收标准：

- 安卓手机可“添加到主屏幕”
- 从桌面图标启动后，浏览器地址栏和底部工具栏不再干扰主要操作
- 书架、详情、阅读器入口可正常打开

### 7.2 第二阶段：是否需要 APK

只有在以下情况成立时，再进入原生安卓壳方案：

- 目标手机浏览器下 PWA 仍无法接受
- 希望用 APK 分发给固定用户安装
- 后续明确要接入原生分享、通知、文件选择等能力

## 8. 当前建议

当前建议不是“二选一立刻拍板上原生”，而是：

1. 先做 PWA
2. 真机验证全屏效果
3. 再决定是否需要原生安卓壳 APK

这条路径最符合当前问题规模，也最符合 Redesk 现有架构。
