02 启动时迁移与 FTS 流程

API 进程启动时 apps/api/src/index.ts → apps/api/src/db.ts → packages/db/src/migrate.ts，按下列顺序执行：

// 启动序列（migrate.ts） 1. setupStorage() // 确认 /data 与 /data/storage 存在并可写 2. migrate(db, { migrationsFolder: 'packages/db/drizzle' }) // Drizzle migrator 读 __drizzle_migrations 与 _journal.json // 对比 hash，跳过已应用，跑未应用 // ⚠️ 一条失败 → 进程崩出 1，启动失败 3. setupFts5(db) // 幂等创建 3 套 FTS5 虚表 + 9 个 trigger // CREATE ... IF NOT EXISTS 安全 // + 回填 notes_fts / highlights_fts (INSERT OR IGNORE) // ⚠️ books_fts 无回填 SQL 4. setupPeriodicBackup(db) // 定时 VACUUM INTO 备份 DB 至多保留 7 份

2.1 Drizzle migrator 的 hash 对比机制

  • 每条 journal 里的迁移都带一个 hash（由 SQL 内容生成）
  • 启动时 migrate() 把 __drizzle_migrations 里的 hash 集合与 journal 对比
  • 未在已应用集合里的迁移 → 执行；已应用的 → 跳过
  • 关键风险：journal 改了 hash（哪怕只是改 created_at 字段），Drizzle 会重跑该迁移

2.2 FTS5 触发器行为分析

软删除不会被 FTS 同步 notes_fts_update / highlights_fts_update 是 AFTER UPDATE 无 WHEN 子句；软删除（UPDATE ... SET deleted_at = ...）会触发 FTS 重索引该行，导致已软删除的笔记/高亮仍出现在全文搜索结果中。
books_fts 启动时无回填 setupFts5 中只对 notes 和 highlights 有 INSERT OR IGNORE INTO ... SELECT ... 回填，books_fts 没有对应回填 SQL。若在 FTS 触发器创建前已存在 books 行，它们不会进 books_fts。
但因为 INSERT / UPDATE / DELETE 触发器齐全，正常运营中新增的书会自动进入 FTS，因此当前观察到的 books_fts = 0 行 仅因为当前业务表本身为空。一旦录入书籍，FTS 会自动跟上。

03 已知兼容性与一致性风险

把"更新优化后旧库不兼容"的现象拆解成 5 个独立风险点，逐条说明触发条件与解法。

3.1 Drizzle 跳跃编号

风险 packages/db/drizzle/meta/_journal.json 当前 idx 30–32 编号为 0014 / 0015 / 0032，中间缺失 0016–0031。journal 被人为压缩过。

如果未来开发者在本地执行 drizzle-kit generate 重排/重生成 journal，可能导致：① journal 与源码 snapshot 错位；② 旧库对比时 hash 不匹配；③ Drizzle 决定重跑某条迁移 → 整表重建（__new_xxx → DROP）模式下容易因旧表已被前一次重建重命名而失败。

3.2 整表重建（__new_xxx）模式的脆弱性

SQLite 不支持 DROP COLUMN / ALTER CONSTRAINT / 改 PK 顺序等，因此 0032_deep_skin 对 12 张核心表使用了"新建 __new_xxx → INSERT SELECT → DROP 旧 → RENAME __new → 正式"模式：

-- 0032_deep_skin 模式片段 CREATE TABLE __new_books (...) -- 新结构 INSERT INTO __new_books(id, owner_id, title, ...) SELECT id, owner_id, title, ... FROM books -- ⚠️ 旧表必须存在 DROP TABLE books ALTER TABLE __new_books RENAME TO books
本次部署就因此失败。旧库中 books 表被人为清理过（残留仅 FTS 虚表壳），0032 跑 INSERT INTO __new_books SELECT ... FROM books 时 SQLite 抛 no such table: books，迁移中断，容器启动失败。

3.3 FTS5 软删除感知缺失

见 §2.2。表现：用户删除一条笔记（软删除 deleted_at），但全文搜索结果中仍能看到该笔记内容片段。

3.4 0032 的 settings 表 PK 顺序变更

0032 把 settings 表 PK 从 (key, owner_id) 改为 (owner_id, key)。语义等价（复合主键），但对老版本生成过同 owner_id 多行的旧库，若原本数据有 PK 冲突可能 INSERT 失败（实际不会因为 unique 不变）。

3.5 物理文件与 DB 分离

数据库迁移不会动到命名卷 /data/storage/ 下的文件。但若把旧库迁移到新代码，物理文件目录结构可能不再匹配（multer 写入的 book_id/... 子目录未必被新 schema 强约定）。建议：升级时同时做一次 §6.4 的"启用下载完整性体检"。

3.6 风险等级总结

风险发生条件影响可检测性
3.1 跳跃编号journal 被人为编辑启动失败高（diff journal）
3.2 整表重建依赖旧表旧库 schema 不完整 / 残留启动失败高（启动前自检）
3.3 FTS 软删除日常使用搜索结果"已删除仍可见"中（功能测试）
3.4 settings PK 顺序跨 0032 升级可能 INSERT 失败低（行为改变）
3.5 物理文件目录DB 与文件目录分别迁移下载 404 / 路径错位中（GET /books/{id}/file）

04 迁移历史版本逐条说明

本节是"更新优化会动到哪些表"的查找表。每条说明三件事：① 改了什么 ② 兼容性影响 ③ 是否需要重建索引/触发器。

0010_storage_mode_a~p（16 段，三态存储策略）

改动：book_files 新增 storage_mode / remote_key / primary_location / sync_status，对应索引与外键重建。
兼容性：纯 ADD COLUMN，理论上向后兼容；但分 16 段执行时若任一中断会处于"半成品"状态。
影响面：book_files、book_covers、status_history、categories、book_tags、book_relations、tags、bookmarks、highlights、notes、reading_progress、settings、topics 全部受影响。

0011 / 0011b（书关联、is_admin 角色）

0011：新建 book_relations 表 + 唯一索引；0011b：users 加 is_admin。
兼容性：纯 ADD，新表 + 新列；向后兼容。

0012_auth_token_model（设置表 PK 改顺序）

改动：settings PK 从 (key, owner_id) 改为 (owner_id, key)。
兼容性：原表用 __new_settings 重建 INSERT SELECT。
注意：老代码生成的库若 __drizzle_migrations 标记为已应用，但实际 PK 顺序是旧的，再次启动不会重跑 — 与 schema drift 风险点。

0013_reading_notes_topics（M2 笔记 + M3 主题）

改动：新增 bookmarks、highlights、notes、reading_progress、topics、topic_books、topic_highlights、topic_notes、topic_segments、topic_entries。创建 notes_fts / highlights_fts 虚表与触发器。
兼容性：纯新增；这是 M2 / M3 的奠基迁移。
特殊：__drizzle_migrations.created_at = 1751616000000（2025-07-05），是唯一一条时间戳倒退的迁移 — 表明 journal 被手动重排过。

0014_add_import_order

改动：books 加 import_order INTEGER NOT NULL DEFAULT 0；同步加索引。
兼容性：纯 ADD COLUMN，DEFAULT 0 自动回填。
本次部署失败点：当旧库 books 表被人为清理，ALTER TABLE books ... 失败。

0015_reading_progress

改动：进度表扩展 + 唯一索引 uq_reading_progress_book_owner。
兼容性：纯索引 / ALTER。

0032_deep_skin（最新 · 整表重建）

改动：一次性重建 12 张表：bookmarks / book_covers / book_files / book_tags / books / categories / settings / topic_books / topic_highlights / topic_notes / users。
books 新增 8 列：entry_reason、source_url、translator、original_title、page_count、genre_category_id、favorited_at、started_at、finished_at。
users 新增 2 列：is_admin、must_change_password。
兼容性：必须 0032 之前的旧表全部完好；任一表缺失 → 整库启动失败。
跳跃编号：journal idx 32 = 0032，中间 0016–0031 已删。

5.2 B 类 · 可重新生成（重建成本低 / 可自动恢复）

06 业务不变量与字段约束

这些约束是"应用怎么用数据库"的硬性约定，写在《数据模型》《决策记录》《AGENTS.md》中。升级时任何破坏这些约束的迁移都应被立即回退。

owner_id 必填 + 边界校验 根实体（users / books / book_files / book_covers / settings / highlights / notes / reading_progress / bookmarks / topics）必须带 owner_id；从属表（book_tags / topic_books / topic_highlights / topic_notes / topic_segments / topic_entries）通过父表继承归属；查询 / 写入必须校验 owner 边界。
deleted_at 软删除 deleted_at TEXT NULL 标记，非物理删除；WHERE deleted_at IS NULL 是主业务查询的默认过滤。
STORED ≠ 删除 books.status 枚举 COLLECTED / PLANNED / READING / READ / STORED，STORED 是独立业务状态，与 deleted_at IS NOT NULL 完全不同。
主题软引用 ON DELETE CASCADE topic_highlights.highlight_id、topic_notes.note_id、topic_segments.* 在原痕物理删除时自动摘除；删主题不动原痕。
ai_assets 隔离 AI 派生内容只走 ai_assets，与用户 notes / highlights 物理隔离；展示层不混入。
进度 1:1 唯一 reading_progress 通过 uq_reading_progress_book_owner 唯一索引，每书每用户一条。
笔记双格式 notes.content_html + content_markdown 同步写；编辑用 HTML（TipTap），导出用 Markdown。
一书一分类 books.category_id 单意外键；不建多对多关联表。
分类用户自定义 不内置通用类型树；分类名称由用户定。当前平级使用，parent_id 留可选不强制。
主阅读文件唯一 book_files.is_primary 同书至多 1 条；无主则首文件自动主，有主不自动切换（WL-002）。
封面来源唯一激活 book_covers.is_active 同书至多 1 条；书籍删除级联清理封面记录与物理文件。
状态时间轴只增 status_history 不更新不删除，APPEND-ONLY；状态变更时插一行。

07 启动失败的恢复路径

按失败症状分 4 类，每类给出"先做哪 3 步"。

7.1 症状：no such table: books（本次部署遇到）

原因：旧库 schema 不完整（缺核心表），但 __drizzle_migrations 记录未跟上。journal 决定重跑某条 ALTER TABLE books ...，旧表不存在而失败。

恢复三步：

  1. 备份现状：cp /data/redesk.db /data/redesk.db.broken（即使坏库也保留以备事后取证）
  2. 清残留：跑 §5.3 的 DROP TABLE IF EXISTS __new_xxx（防御性）
  3. 二选一：
      路径 A — 接受全量重建：rm -f /data/redesk.db /data/redesk.db-shm /data/redesk.db-wal，重启容器；
      路径 B — 从备份恢复：用 §7.6 的 ZIP / VACUUM INTO 备份覆盖 redesk.db，重启。

7.2 症状：__drizzle_migrations 字段不存在 / hash 不匹配

原因：journal 改过 hash（如重排序、改 created_at），Drizzle 误判未应用，重跑迁移失败。

恢复：

  1. 备份 redesk.db
  2. 备份 __drizzle_migrations 表的内容到外部文件
  3. 用 SQLite CLI 对比 journal 中每条 hash 与备份里的 hash，找出"理论上已应用但 Drizzle 误判"的条目
  4. 若无法对齐，建议接受全量重建并恢复 A 类表（§5.1）

7.3 症状：UNIQUE constraint failed: books.id（重建中途崩溃）

原因：0032 类整表重建在 INSERT INTO __new_books SELECT * FROM books 之前已经 DROP 旧表或部分完成。

恢复：

  1. 立即停服（docker compose stop）
  2. 跑 §5.3 清理残留的 __new_xxx
  3. 若 books 表本身已 DROP，从备份恢复；否则重启

7.4 症状：FTS 触发器缺失但虚表存在

原因：手动清理过触发器或 setupFts5 在迁移失败前未跑到。

恢复：直接重启一次容器即可。setupFts5 幂等。

7.5 症状：books_fts 行数 0 但 books 有数据

原因：在 setupFts5 创建触发器之前已经写入 books，触发器没有回溯历史数据。

恢复：跑一次手动回填（建议作为后续改进纳入 setupFts5）：

INSERT INTO books_fts(rowid, title, author, isbn)
  SELECT id, title, author, isbn FROM books
  WHERE deleted_at IS NULL
  ON CONFLICT(rowid) DO NOTHING;

7.6 推荐的预防 / 备份策略

  • 升级前：GET /api/v1/backup/manual 触发全量 ZIP（DB + 文件 + Markdown 副本）
  • 升级后：保留旧 ZIP 至少 7 天；容器内 setupPeriodicBackup 每天 VACUUM INTO 最多保留 7 份
  • 回滚：API 提供了"最近 7 份 SQLite 备份"恢复入口，文件名带时间戳，可选择覆盖 redesk.db
  • 原则：数据库迁移失败 = 启动失败 = 服务不可用；任何想"自动忽略迁移错误继续启动"的实现都应被拒绝（决策记录 · 一致性原则）

08 升级前自检 Checklist

把以上结论凝练为一份"动手前 6 步"。

  1. 备份：先用 API 触发手动全量 ZIP，同时 cp 容器内 redesk.db + redesk.db-wal + redesk.db-shm 一份到主机（即使升级顺利也保留 7 天）。
  2. 健康自检：跑 sqlite3 redesk.db "PRAGMA integrity_check; PRAGMA foreign_key_check;"，两者都必须返回 ok / 空集。
  3. 核心表存在性：跑 SELECT name FROM sqlite_master WHERE type='table' AND name IN ('books','book_files','users','settings','highlights','notes','reading_progress','topics') ORDER BY name;，缺失任意一条 → 升级前需要先恢复。
  4. 残留清理：跑 §5.3 的 DROP TABLE IF EXISTS __new_xxx，避免新迁移被"对象已存在"挡住。
  5. journal 视觉对比：升级前 git diff packages/db/drizzle/meta/_journal.json，关注 hash 变化、idx 重排、新增跳跃编号。任何跳跃都应人工 review。
  6. 物理文件与 DB 同步：确认 /data/storage/ 备份与 DB 备份在同一次操作里导出，不要分两次。
