# 书籍匹配与批量上传重设计方案

> 目的：重做 Redesk 当前“未关联文件 -> 书籍匹配”的流程与能力，使批量上传后的下一步自然衔接到匹配，并把匹配从“前端猜测 + 单个确认”改为“后端候选生成 + 批量确认”。

## 1. 结论摘要

当前实现的主要问题不是某个细节 bug，而是整体设计层级不对：

1. “批量上传”和“书籍匹配”被拆成了两个割裂动作，上传结束后没有自然下一步。
2. “匹配”实质上没有后端识别能力，前端只是按文件名做字符串近似排序，再调用一个纯关联接口完成落账。
3. 批量上传可以一次传多个文件，但匹配仍然是逐个文件打开弹窗、逐个确认，流程在高频场景下明显不可用。

因此建议采用以下重设计方向：

1. 把“上传完成后的匹配”升级为上传流程的第二步，而不是让用户自己再去文件库补操作。
2. 把“候选书籍生成”下沉到后端，前端只负责展示候选、批量确认和人工修正。
3. 让匹配能力同时支持单文件与多文件，但以“批量匹配工作台”为主入口。
4. 匹配规则分层：文件名标准化匹配作为基础层，EPUB 元数据匹配作为增强层，歧义时要求人工确认，不做静默自动关联。

## 2. 当前实现现状

基于当前仓库代码，现状如下：

### 2.1 上传流程现状

- 批量上传入口在 `apps/web/src/routes/settings/storage-tab.tsx` 的 `BatchUploadCard`。
- 该弹窗会逐个调用 `POST /files/unassociated` 上传到未关联文件池。
- 上传完成后只显示成功/失败状态，没有进入“下一步匹配”的引导，也没有批量匹配入口。

### 2.2 匹配流程现状

- 文件库入口在 `apps/web/src/routes/file-library/index.tsx`。
- 匹配候选构建逻辑在 `apps/web/src/routes/file-library/match-utils.ts`。
- 当前候选排序只依赖：
  - `original_filename`
  - 书名字符串相似度
  - 作者字符串相似度
  - 少量 token 命中
- 后端 `apps/api/src/routes/files.ts` 中的 `POST /files/:id/match` 只是把未关联文件写入指定 `book_id`，并不会自己判断该匹配谁。

### 2.3 当前设计的核心缺陷

1. 匹配能力停留在前端，无法复用，也无法形成稳定规则版本。
2. 批量上传没有批量匹配闭环，用户被迫从“上传上下文”跳到“文件库清理上下文”。
3. 文件名规则对“书名在前，后面跟作者、站点、系列、版本说明”的真实样本处理不够。
4. EPUB 作为结构化格式，系统已经能解包抽封面，但还没有利用包内元数据辅助匹配。

## 3. 样本验证结论

本次已用 `dataLab/` 中的样本 EPUB 做了只读验证，确认这些文件内部通常能直接提取到比文件名更干净的元数据，至少包括：

- `dc:title`
- `dc:creator`
- 部分文件还有 `dc:publisher`
- 部分文件还有 `dc:identifier`

样本结果举例：

| 文件名 | EPUB 内 title | EPUB 内 creator |
| --- | --- | --- |
| `不原谅也没关系：复杂性创伤后压力综合征自我疗愈圣经 ([美] 皮特·沃克) (Z-Library).epub` | `不原谅也没关系` | `皮特·沃克` |
| `从一到无穷大 (乔治·伽莫夫 (George Gamow)) (Z-Library).epub` | `从一到无穷大` | `乔治·伽莫夫` |
| `博弈论与生活 ([英]兰·费雪) (Z-Library).epub` | `博弈论与生活` | `[英]兰·费雪` |
| `打造第二大腦：多一個數位大腦，資訊超載時代的高效能知識管理術 = ... .epub` | `打造第二大腦` | `提亞戈．佛特 Tiago Forte` |

这说明：

1. “上传文件名带站点后缀导致无法命中”的问题，不能只靠继续调前端字符串算法解决。
2. EPUB 元数据匹配不是高成本幻想，而是可直接复用现有解包能力的现实增强项。
3. 对 EPUB 而言，书内元数据应进入匹配流程，至少作为“精准匹配”的依据之一。

## 4. 设计目标

本次重设计建议以以下目标为准：

1. 上传结束后，用户能立刻看到匹配入口，但是否继续匹配由用户自己决定。
2. 对一批文件，系统能一次给出整批推荐，而不是逐个打开弹窗。
3. 高置信候选可以一键批量应用，中低置信候选保留人工审核。
4. 匹配规则必须可解释，用户能看到“为什么推荐这本书”。
5. 不做静默自动关联，避免误绑污染书籍文件关系。
6. 兼容现有“文件池”设计，不推翻未关联文件池，只重做其入口和处理方式。

## 5. 推荐的交互方案

## 5.1 总体方向

推荐把“匹配”做成一个可复用的**匹配工作台**，而不是继续做“单文件弹窗”。

这个工作台可以被两个入口调用：

1. 批量上传完成后直接进入。
2. 文件库中点击“处理未关联文件”时进入。

这样可以同时满足你提到的两种诉求，但主推荐是：

- 不再只是“上传完成后给一个跳转按钮”
- 而是“上传完成后在同一上下文里明确给出下一步匹配入口，但不强制立刻进入”

## 5.2 上传后的推荐流程

推荐改为三段式，但第 3 步是**可选收口动作**，不是强制步骤：

1. 选择文件
2. 上传文件
3. 匹配书籍（可选）

具体行为：

1. 批量上传弹窗上传成功后，不强制跳入匹配页。
2. 上传结果区明确展示两类后续动作：
   - `继续匹配这些文件`
   - `暂时完成，稍后处理`
3. 如果用户选择继续匹配，再进入“匹配书籍”工作台。
4. 工作台展示刚刚上传成功的全部未关联文件。
5. 每一行显示：
   - 文件名
   - 解析出的关键信息
   - 推荐书籍
   - 置信度
   - 推荐依据
   - 可切换候选
6. 顶部提供：
   - `全部应用高置信推荐`
   - `只看待确认`
   - `跳过低置信`
   - `稍后处理`

这样用户上传完一批文件后：

1. 如果当前只想先把文件放进系统，可以直接结束。
2. 如果想趁上下文还在，立刻把未关联文件处理掉，也能一键进入匹配。

这比“强制上传后马上匹配”更符合真实使用习惯。

## 5.3 文件库中的补救流程

文件库页保留，但角色要调整为：

- 历史未处理文件的清理入口
- 上传后中断任务的补救入口
- 低置信文件的人工复核入口

文件库中的“匹配”不再是单个文件弹窗主流程，而是：

1. 页面顶部对未关联文件给出显眼提示
2. 点击“开始匹配”后打开同一个匹配工作台
3. 工作台默认批量处理当前未关联文件

## 5.4 为什么不建议直接上传后自动关联

不建议默认“上传成功即自动绑定书籍”，原因如下：

1. 书库里可能存在同书不同版本、同名不同书、套装与单册并存。
2. 一旦绑错，会污染书籍详情页、主文件判断、后续阅读入口。
3. 用户对文件资产的容错通常低于对普通列表推荐的容错。

因此建议：

- 系统可以自动给出推荐
- 但关联动作必须由用户显式确认

## 6. 匹配能力重设计

## 6.1 设计原则

匹配能力应迁移到后端，前端不再自己决定谁最像谁。

前端职责应变为：

1. 发起候选请求
2. 展示候选结果
3. 支持人工修正
4. 批量提交确认

后端职责应变为：

1. 解析文件特征
2. 生成候选书籍
3. 计算置信度
4. 返回推荐依据

## 6.2 匹配分层

建议把匹配规则分成四层，逐层增强。

### A. 文件名标准化层

这是基础层，所有格式都适用。

标准化建议包括：

1. 去扩展名
2. 去站点尾巴，如 `Z-Library`
3. 去常见噪音词，如“完整版”“扫描版”“文字版”“校对版”
4. 去括号中的发行来源信息、格式标记、卷号说明
5. 统一中英文括号、空格、连字符、分隔符
6. 保留书名主体与作者主体

这层重点解决你的 2.1 问题：

- 文件名前几个字符已经是书名，但后面挂了作者或站点后缀，当前系统仍然命不中

对这类文件，规则不该要求“整串高度相似”，而应支持：

- “文件名标准化后包含书名主体”
- “文件名以书名主体开头”

这两种都应视为强信号。

### B. 书名模糊匹配层

这是你提出的 2.2，对所有格式都应支持。

建议采用以下组合，而不是单一相似度：

1. 书名完整包含
2. 书名前缀命中
3. 书名关键词命中率
4. 字符双元组相似度
5. 词序保持奖励

判定原则建议如下：

1. 若标准化文件名包含标准化书名，且候选差距明显，可直接判为高置信。
2. 若只命中部分关键词，但关键词覆盖高且排序稳定，判为中置信。
3. 若多个候选相似度接近，即使分数不低，也必须降级为“需确认”。

### C. 作者辅助层

作者不应单独决定匹配，但应作为强加分项。

原因：

1. 同名书存在，但“书名 + 作者”重复概率显著下降。
2. 有些文件名把作者放在括号中，适合做辅助确认。

建议规则：

1. 书名高命中 + 作者命中：高置信
2. 书名中等命中 + 作者命中：可升为中高置信
3. 仅作者命中、书名弱：不能直接推荐

### D. EPUB 元数据增强层

这层只对 EPUB 开启，建议优先做。

建议提取：

1. `title`
2. `creator`
3. `publisher`
4. `identifier`

用法：

1. 若 `title` 与库中书名高一致，直接作为强信号。
2. 若 `title + creator` 同时命中，优先级高于文件名模糊匹配。
3. 若 `identifier` 能识别为 ISBN，并与书籍 `isbn` 一致，可直接判为最高置信。

这层适合归入你说的“精准匹配”。

## 6.3 推荐的匹配模式定义

当前前端已有“保守 / 平衡 / 宽松”概念，但只在本地字符串打分里使用。建议保留这个产品概念，但改由后端定义。

### 保守

- 只接受高确定性结果
- 适合一键应用
- 宁可漏，不可错

### 平衡

- 默认模式
- 高置信自动勾选
- 中置信待确认

### 宽松

- 尽量给出候选
- 适合大批量清理历史文件
- 但必须把风险标识做得更醒目

## 7. 批量匹配工作台设计

## 7.1 行级结构

每个待匹配文件一行，建议展示：

1. 原始文件名
2. 提取摘要
   - 规范化标题
   - 规范化作者
   - EPUB 标题 / 作者（如果有）
3. 推荐书籍
4. 置信等级
5. 推荐依据
6. 操作
   - 接受推荐
   - 更换候选
   - 暂不处理
   - 新建书籍

## 7.2 顶部批量操作

建议提供：

1. `应用全部高置信推荐`
2. `应用当前已勾选项`
3. `仅显示未处理`
4. `仅显示需确认`
5. `切换匹配模式`

## 7.3 匹配结果分级

建议将结果分为三类：

### 高置信

- 可默认勾选
- 支持批量应用

### 需确认

- 推荐保留人工确认
- 要明确显示“存在相近候选”

### 未命中

- 保持未关联
- 支持：
  - 手动搜索书籍
  - 直接新建书籍
  - 稍后处理

## 8. 后端接口建议

当前 `POST /files/:id/match` 只负责落账，建议继续保留，但新增“候选生成”和“批量应用”接口。

## 8.1 候选生成接口

建议新增：

- `POST /files/match/candidates`

请求体建议：

```json
{
  "file_ids": [101, 102, 103],
  "mode": "balanced"
}
```

返回建议：

```json
{
  "data": [
    {
      "file_id": 101,
      "derived": {
        "filename_title": "从一到无穷大",
        "filename_author": "乔治·伽莫夫",
        "epub_title": "从一到无穷大",
        "epub_author": "乔治·伽莫夫",
        "epub_identifier": "3485298853"
      },
      "recommended_book_id": 12,
      "confidence": "high",
      "reason": "EPUB标题命中，作者命中，文件名起始段命中",
      "candidates": [
        { "book_id": 12, "title": "从一到无穷大", "score": 0.96 },
        { "book_id": 87, "title": "从零到一", "score": 0.41 }
      ]
    }
  ]
}
```

## 8.2 批量应用接口

建议新增：

- `POST /files/match/apply-batch`

请求体建议：

```json
{
  "items": [
    { "file_id": 101, "book_id": 12 },
    { "file_id": 102, "book_id": 35 }
  ]
}
```

原因：

1. 前端不需要循环调用单文件接口，交互更顺。
2. 后端可统一校验 owner 边界。
3. 可以统一返回成功数、失败数、冲突明细。

## 8.3 是否需要改现有单文件接口

现有接口可保留，语义可调整为：

- `POST /files/:id/match`：单文件确认关联
- `POST /files/match/candidates`：候选生成
- `POST /files/match/apply-batch`：批量落账

这样兼容现有调用方，也便于逐步迁移。

## 9. 数据层建议

## 9.1 最小改法

如果希望第一轮先快速落地，可以先不改表：

1. 上传后候选生成时，实时读取 `book_files.original_filename`
2. 对 EPUB 现读现解析
3. 返回候选，不持久化解析结果

优点：

1. 改动小
2. 可以先验证效果

缺点：

1. 每次匹配都会重复解析 EPUB
2. 文件库列表无法直接展示“已解析标题/作者”

## 9.2 推荐改法

如果希望这套能力长期稳定，建议给 `book_files` 增加少量派生字段，缓存提取结果：

1. `detected_title`
2. `detected_author`
3. `detected_identifier`
4. `metadata_extracted_at`

这些字段不是书籍真元数据，只是“文件侧识别摘要”，用于匹配与展示。

这样做的好处：

1. 同一文件不用重复解析
2. 文件库可直接显示“识别到：书名/作者”
3. 后续若要做“自动发现未关联文件”或“定时复扫”，有落点可用

## 10. 推荐的实施顺序

建议分两阶段实施，而不是一次把所有想法同时上完。

## 第一阶段：先打通流程

目标：让现在的用户至少能顺滑完成“上传后批量匹配”。

范围：

1. 批量上传成功后增加“进入匹配工作台”
2. 工作台支持多文件列表
3. 后端提供候选生成接口
4. 文件名标准化 + 模糊匹配下沉到后端
5. 支持批量应用高置信结果

这一阶段先不强依赖表结构调整，也先不要求 EPUB 元数据持久化。

## 第二阶段：再提准确率

目标：把 EPUB 匹配率明显拉高。

范围：

1. 加入 EPUB `title/creator/identifier` 提取
2. 识别 ISBN 并直连 `books.isbn`
3. 视情况加入 `detected_*` 缓存字段
4. 优化候选原因文案与歧义降级规则

## 11. 关键规则建议

以下规则建议直接作为产品红线：

1. 未经用户确认，不静默自动关联。
2. 高分但存在接近候选时，必须降级为“需确认”。
3. EPUB 元数据优先级应高于原始文件名噪音串。
4. 匹配是“生成候选”，不是“替用户做决定”。
5. 文件匹配成功后仍遵循现有主文件规则：无主则升，有主不动。

## 12. 与当前需求点的对应

### 对应问题 1：流程不通畅

解决方式：

1. 批量上传改成“上传完成后提供匹配入口”的两段式流程
2. 上传完成后可一键进入匹配工作台，但允许直接关闭
3. 文件库中的匹配入口复用同一个工作台
4. 支持整批文件统一处理

### 对应问题 2.1：文件名后缀干扰匹配

解决方式：

1. 强化文件名标准化
2. 把“书名在开头”作为强信号
3. EPUB 文件增加包内元数据提取

### 对应问题 2.2：希望按关键字段模糊匹配

解决方式：

1. 后端做书名关键词命中率与包含关系判断
2. 允许“关键字段命中即进入候选”
3. 用置信分级而不是简单二元“匹配/不匹配”

### 对应问题 2.3：更高效或更精准的方式

建议如下：

1. 第一优先：后端统一匹配引擎
2. 第二优先：EPUB 元数据增强
3. 第三优先：批量工作台 + 批量应用

其中最值得优先做的是前两项，因为它们同时解决“流程差”和“准确率差”。

## 13. 实施前置注意事项

1. `dataLab/` 当前未见被 `.gitignore` 排除；由于该目录用于本地样本验证，实现前应补充忽略规则，避免误提交。
2. 匹配工作台属于流程重设计，前端不应继续在多个地方各写一套匹配逻辑，而应抽成统一能力。
3. 若要持久化 EPUB 提取结果，需先同步更新《数据模型》《API 接口》《开发执行计划》相关文档。

## 14. 最终建议

本次需求不建议只做“上传完成后加一个跳转按钮”这种最小修补，因为那只能缓解入口断裂，解决不了批量匹配与准确率问题。

同时也不建议把“上传后立即匹配”做成强制流程，因为上传文件与处理匹配虽然相关，但并不总是同一次任务里的必做动作。

推荐落地方向是：

1. 以“匹配工作台”统一上传后可选匹配与历史清理匹配。
2. 以后端候选生成替代前端本地猜测。
3. 第一阶段先做文件名标准化和批量处理。
4. 第二阶段补 EPUB 元数据精准匹配。

这是当前成本、体验和准确率之间最平衡的方案。
