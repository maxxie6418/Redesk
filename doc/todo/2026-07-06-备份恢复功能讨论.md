## 1. 用户需求

用户希望完善 Redesk 的备份与恢复能力，核心目标不是单一数据导出，而是覆盖整个项目运行所需的配置与内容。

需求范围包括：

- 整个项目配置的备份与恢复。
- 内容数据的备份与恢复。
- 支持全量恢复。
- 评估是否支持增量恢复。
- 评估是否支持分模块恢复，例如：
  - 书籍信息；
  - 书籍文件；
  - 分类与标签；
  - 笔记；
  - 高亮；
  - 书签；
  - 阅读进度；
  - 主题阅读；
  - 系统设置；
  - AI / OSS 等外部服务配置。
- 判断当前数据结构或共享类型是否需要优化。

用户当前场景：即将更换电脑，需要先把需求、现状和建议落成讨论文档，作为后续继续开发的交接依据。

## 2. 当前探查到的实现现状

### 2.1 文档层现状

`doc/API接口.md` 中已经记录了导出与备份相关接口：

- `GET /export/books`：导出书籍元数据。
- `GET /export/notes`：预留导出笔记。
- `POST /import/notes`：预留外部笔记导入。
- `POST /backup/full`：生成完整备份 ZIP。
- `GET /backup/list`：列出自动备份文件。
- `POST /backup/trigger`：触发 SQLite 自动备份。

当前文档中尚未定义恢复接口，例如恢复预检、恢复执行、恢复结果查询等。

### 2.2 后端实现现状

当前主要实现集中在：

- `apps/api/src/routes/export.ts`
- `apps/api/src/routes/system.ts`
- `apps/api/src/routes/settings.ts`

已具备的能力：

- 支持书籍元数据导出 JSON / CSV。
- 支持生成完整备份 ZIP。
- 完整备份 ZIP 当前包含：
  - `redesk.db`；
  - `storage/` 下的本地文件；
  - 书籍 Markdown 副本。
- 支持自动 SQLite 备份，使用 `VACUUM INTO` 生成数据库备份文件。
- 支持列出已有自动备份文件。
- 设置接口已有敏感配置脱敏逻辑。

当前缺口：

- 没有恢复接口。
- 没有备份包 `manifest.json`。
- 没有恢复预检流程。
- 没有恢复执行前的安全保护流程。
- 没有恢复失败回滚策略。
- 没有分模块恢复的范围定义。
- 没有增量备份链或变更日志。

### 2.3 前端实现现状

当前主要入口在：

- `apps/web/src/routes/settings/backup-tab.tsx`
- `apps/web/src/routes/settings/page.tsx`

已具备的能力：

- 设置页已有备份相关页签。
- 用户可以触发完整备份下载。
- 用户可以触发 SQLite 自动备份。
- 用户可以查看自动备份列表。

当前缺口：

- 没有上传备份包入口。
- 没有恢复预检界面。
- 没有恢复范围选择界面。
- 没有敏感配置恢复确认界面。
- 没有恢复风险提示与结果报告。

### 2.4 数据模型现状

当前数据模型整体适合全量备份恢复。

核心数据主要在 SQLite 中：

- 书籍：`books`
- 文件元信息：`book_files`、`book_covers`
- 分类与标签：`categories`、`tags`、`book_tags`
- 阅读数据：`reading_progress`、`highlights`、`notes`、`bookmarks`
- 主题阅读：`topics`、`topic_books`、`topic_highlights`、`topic_notes`、`topic_segments`、`topic_entries`
- 设置：`settings`
- 用户：`users`

文件本体在 `storage/` 目录中，数据库保存相对路径、checksum、大小、存储模式和同步状态等信息。

判断：

- 全量恢复不需要大改现有业务表。
- 文件恢复需要更严格的文件清单和完整性校验。
- 设置恢复需要区分普通设置、敏感设置、高风险访问控制设置。
- 分模块恢复需要处理模块依赖和 ID 映射。
- 真正增量恢复需要额外设计备份链或变更日志。

## 3. 能力分层判断

### 3.1 全量恢复

可以做，且建议第一阶段优先实现。

语义：用一个备份包把当前 Redesk 实例恢复到备份时的完整状态。

建议覆盖：

- 数据库；
- 书籍文件；
- 封面文件；
- 阅读进度；
- 高亮；
- 笔记；
- 书签；
- 主题阅读；
- 设置；
- 用户信息；
- 存储配置。

推荐流程：

```text
上传备份包
  ↓
解析 manifest.json
  ↓
恢复预检
  ↓
展示将恢复的内容和风险
  ↓
用户确认
  ↓
自动备份当前实例
  ↓
替换数据库和 storage 文件
  ↓
执行迁移/校验
  ↓
提示重启或自动重载
```

优势：

- 与 SQLite 整库备份天然匹配。
- 不需要处理复杂 ID 重映射。
- 主题、高亮、笔记等内部引用不会断。
- 最适合“换电脑”“迁移实例”“灾难恢复”这类场景。

风险：

- 会覆盖当前实例数据。
- 必须有恢复前保护备份。
- 必须先做备份包完整性校验。

### 3.2 分模块恢复

可以做，但不建议与第一版全量恢复混在一起一次完成。

可选模块：

- 书籍信息；
- 书籍文件；
- 封面；
- 分类与标签；
- 阅读进度；
- 高亮；
- 笔记；
- 书签；
- 主题阅读；
- 系统设置；
- AI / OSS 配置；
- 用户与权限。

模块依赖关系：

- 设置相对独立，最容易单独恢复。
- 书籍信息依赖分类、标签和书籍关系。
- 书籍文件依赖书籍和文件路径策略。
- 笔记、高亮、书签、阅读进度依赖书籍。
- 主题阅读依赖书籍、高亮、笔记和章节片段，是最复杂的分模块恢复对象。

建议第一批支持的分模块恢复：

1. 设置恢复。
2. 书籍信息恢复。
3. 分类与标签恢复。
4. 书籍文件恢复。
5. 笔记、高亮、书签恢复。

建议暂缓：

- 主题阅读分模块恢复。
- AI 派生内容分模块恢复。
- 云端文件自动恢复。
- 多用户跨用户合并。

### 3.3 增量恢复

可以做，但建议第三阶段再考虑。

增量恢复有两种含义：

1. 从一个备份包里只恢复当前实例缺少的新增内容。
2. 使用备份链，例如先恢复全量包，再依次应用每日增量包。

第一种更接近“分模块合并恢复”，可以在第二阶段顺带支持一部分。

第二种是真正的增量备份链，复杂度较高，需要记录：

- 基线备份 ID；
- 哪些表发生变化；
- 哪些文件新增、修改、删除；
- 删除操作如何表达；
- 增量链缺失时如何处理；
- 与当前实例冲突时如何处理。

当前 Redesk 没有通用 change log 表，因此暂不建议第一阶段实现真正增量备份链。

## 4. 备份包结构建议

当前完整备份 ZIP 更接近“下载留档”，还不是严格的“可恢复归档”。建议升级为稳定结构：

```text
manifest.json
database/redesk.db
storage/books/...
storage/covers/...
exports/books/*.md
exports/books.json
```

其中 `manifest.json` 是恢复能力的基础。

建议 manifest 包含：

```json
{
  "format_version": 1,
  "app": {
    "name": "Redesk",
    "version": "2.0.1"
  },
  "created_at": "2026-07-06T00:00:00.000Z",
  "backup_type": "full",
  "database": {
    "path": "database/redesk.db",
    "schema_version": "当前迁移版本"
  },
  "content": {
    "books": 0,
    "files": 0,
    "covers": 0,
    "notes": 0,
    "highlights": 0,
    "topics": 0
  },
  "settings": {
    "included": true,
    "secrets_included": false
  },
  "files": [
    {
      "kind": "book_file",
      "relative_path": "storage/books/example.epub",
      "size_bytes": 1234567,
      "checksum": "sha256..."
    }
  ]
}
```

manifest 用途：

- 恢复前展示备份包内容。
- 判断应用版本是否兼容。
- 判断数据库 schema 是否需要迁移。
- 校验文件是否缺失。
- 校验 checksum 是否匹配。
- 判断是否包含敏感配置。
- 为分模块恢复提供模块计数与范围信息。

## 5. API 设计建议

建议保留现有备份接口，并补充恢复接口。

### 5.1 备份接口

继续保留：

```text
POST /backup/full
GET /backup/list
POST /backup/trigger
```

建议增强：

- `POST /backup/full` 生成新版 ZIP 结构。
- ZIP 中增加 `manifest.json`。
- 返回文件名、大小、创建时间、备份类型。

### 5.2 恢复接口

建议新增：

```text
POST /backup/restore/preview
POST /backup/restore
```

`POST /backup/restore/preview`：

- 接收上传的备份 ZIP。
- 解压到临时目录。
- 校验 manifest。
- 校验数据库是否可打开。
- 校验文件完整性。
- 返回恢复预检结果。
- 不修改当前数据库和 storage。

`POST /backup/restore`：

- 接收预检阶段生成的 `restore_token`。
- 接收恢复模式与恢复范围。
- 执行恢复前保护备份。
- 执行全量替换或模块导入。
- 返回恢复结果。

## 6. 共享类型建议

建议在 `packages/shared` 中新增或补齐以下 Zod schema，避免前后端重复维护恢复协议。

### 6.1 备份范围

```ts
export const backupScopeSchema = z.object({
  books: z.boolean().default(true),
  files: z.boolean().default(true),
  covers: z.boolean().default(true),
  categories: z.boolean().default(true),
  tags: z.boolean().default(true),
  reading_progress: z.boolean().default(true),
  highlights: z.boolean().default(true),
  notes: z.boolean().default(true),
  bookmarks: z.boolean().default(true),
  topics: z.boolean().default(true),
  settings: z.boolean().default(true),
  users: z.boolean().default(false),
  secrets: z.boolean().default(false),
});
```

### 6.2 恢复模式

```ts
export const restoreModeSchema = z.enum([
  'replace_all',
  'merge_modules',
]);
```

### 6.3 恢复预检结果

```ts
export const restorePreviewSchema = z.object({
  restore_token: z.string(),
  backup_id: z.string(),
  app_version: z.string(),
  created_at: z.string(),
  compatible: z.boolean(),
  warnings: z.array(z.string()),
  counts: z.record(z.number()),
  conflicts: z.array(z.object({
    module: z.string(),
    type: z.string(),
    message: z.string(),
  })),
});
```

### 6.4 恢复执行请求

```ts
export const restoreExecuteSchema = z.object({
  restore_token: z.string(),
  mode: restoreModeSchema,
  scope: backupScopeSchema,
  conflict_strategy: z.enum(['skip', 'overwrite', 'rename']).default('skip'),
  include_secrets: z.boolean().default(false),
  create_pre_restore_backup: z.boolean().default(true),
});
```

## 7. 数据结构是否需要优化

### 7.1 不建议现在大改业务表

当前核心数据结构已经适合全量备份恢复：

- SQLite 单文件适合整库备份与迁移。
- 文件表已有 `local_path`、`remote_key`、`storage_mode`、`primary_location`、`sync_status`、`checksum`。
- `settings` 键值表适合配置项演进。
- 主题阅读引用关系在整库恢复下不会断。
- `owner_id` 已预留多用户边界。

因此不建议为了备份恢复重构现有主业务表。

### 7.2 需要补充的结构和约定

建议补充：

- 备份包 manifest。
- 恢复预检结果类型。
- 恢复执行请求类型。
- 文件完整性清单。
- settings key 常量。
- sensitive settings key 常量。
- restorable settings key 常量。
- exportable settings key 常量。

### 7.3 可暂缓的表结构

以下表或结构暂不建议第一阶段新增：

- `backup_jobs`：除非恢复任务需要长时间后台运行和历史记录。
- `change_log`：除非要做真正增量备份链。
- 强类型 settings 表：当前键值表更适合配置演进。

## 8. 安全与风险控制

### 8.1 恢复前必须自动备份当前状态

恢复执行前必须自动生成当前实例保护备份，建议包含：

- 当前 `redesk.db`；
- 当前 `storage/` 快照或压缩包；
- 恢复操作元信息。

命名示例：

```text
pre-restore-2026-07-06-153000.zip
```

### 8.2 恢复必须使用临时目录

建议流程：

```text
storage/tmp/restore-{token}/
```

在临时目录完成：

- ZIP 解压；
- manifest 校验；
- DB 打开测试；
- 文件 checksum 校验；
- 恢复预检结果生成。

只有用户确认后，才允许替换正式数据库和正式 storage。

### 8.3 敏感配置必须单独确认

敏感配置包括但不限于：

- `llm_api_key`
- `oss_access_key`
- `oss_secret_key`
- session / auth 相关 secret

默认建议：

- 普通备份可以包含敏感配置，但 manifest 必须声明。
- 恢复时默认不恢复敏感配置。
- 用户明确勾选后才恢复敏感配置。
- 如果未来支持“可分享备份包”，必须支持导出不含密钥的备份包。

## 9. 推荐分期

### 9.1 第一阶段：可靠全量恢复

目标：先解决换电脑、灾难恢复、迁移实例的核心场景。

范围：

- 新版完整备份 ZIP 结构。
- `manifest.json`。
- 恢复预检接口。
- 全量恢复执行接口。
- 恢复前自动保护备份。
- 设置页上传备份包入口。
- 设置页恢复预检结果展示。
- 设置页确认恢复。
- 恢复结果报告。

不做：

- 分模块恢复。
- 合并恢复。
- 真正增量备份链。
- 主题阅读单独恢复。

### 9.2 第二阶段：分模块恢复

目标：支持从备份包中选择性恢复部分内容。

优先模块：

1. 设置。
2. 书籍信息。
3. 分类与标签。
4. 书籍文件。
5. 笔记、高亮、书签。

暂缓模块：

- 主题阅读。
- AI 派生内容。
- 多用户数据合并。
- 云端文件自动同步。

### 9.3 第三阶段：增量备份链

目标：在备份体积、远端同步流量或时间点恢复需求明确后，再设计真正增量备份链。

可能需要新增：

- 备份快照记录。
- 变更日志。
- 文件新增/修改/删除清单。
- 增量链完整性校验。

## 10. 建议验收标准

### 10.1 全量备份

- 能生成包含 manifest、数据库和 storage 文件的完整备份包。
- manifest 能准确记录应用版本、备份时间、备份类型、内容计数和文件清单。
- 备份包可以被恢复预检接口识别。

### 10.2 全量恢复

- 上传备份包后可以完成预检。
- 预检不会修改当前数据。
- 预检能发现 manifest 缺失、数据库损坏、文件缺失、checksum 不一致等问题。
- 用户确认前不会执行恢复。
- 恢复前会自动备份当前状态。
- 恢复成功后数据库、书籍文件、设置和内容数据一致。
- 恢复失败时不会破坏当前实例。

### 10.3 分模块恢复

- 用户可以选择恢复范围。
- 设置恢复支持敏感配置单独确认。
- 笔记、高亮、书签恢复能处理找不到书籍的情况。
- 冲突处理策略清晰，例如跳过、覆盖、重命名。
- 恢复结果报告能列出新增、跳过、失败、冲突项。

## 11. 推荐决策

建议后续按以下决策推进：

1. Redesk 恢复功能分三层：全量恢复、分模块恢复、增量恢复。
2. 第一阶段只做可靠全量恢复，保证换电脑和灾难恢复场景可用。
3. 第一阶段必须增加 `manifest.json`，否则恢复流程缺少稳定契约。
4. 第一阶段不改主业务表，优先补共享类型、备份包结构和恢复接口。
5. 第二阶段再做分模块恢复，先做设置、书籍信息、分类标签、笔记高亮。
6. 主题阅读分模块恢复暂缓，因为它依赖书籍、高亮、笔记和章节片段，引用关系更复杂。
7. 真正增量备份链暂缓，除非后续明确出现备份体积、远端同步或时间点恢复需求。

## 12. 后续执行建议

下一步建议先确认第一阶段范围：

- 是否第一阶段只做全量恢复。
- 是否完整备份默认包含敏感配置。
- 是否恢复时默认排除敏感配置。
- 是否恢复完成后要求用户手动重启服务。
- 是否需要在 UI 中展示备份包详细内容与风险。

确认后再进入实现计划，建议实施顺序：

1. 补 `packages/shared` 中的备份 manifest 与恢复 schema。
2. 给 `POST /backup/full` 增加 manifest 生成。
3. 新增恢复预检测试。
4. 实现恢复预检接口。
5. 新增全量恢复执行测试。
