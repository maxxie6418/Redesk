## 1. 打磨边界与退出标准

### 1.1 参照系

当前使用 Notion 作为书籍管理工具。Notion 书单具备以下能力：

- 基本的书籍存储（**不能存文件**）—— 意义上更接近一个书单/书库
- 可上传封面图，以卡片形式呈现
- 记录动态数据：已读/未读状态、评分、阅读意愿
- 记录固定信息：分类（注意：项目已确认一书一分类模型，见《决策记录》）、作者、豆瓣链接、评分、页数
- 场景：当要收藏一本当前觉得有价值的书时使用

### 1.2 退出标准（已确定）

**Redesk 能自然接替 Notion 进行书籍管理，且具备优势，第一阶段打磨即算完成。**

对比 Notion 的核心优势：
- Redesk 能存储实际书籍文件（Notion 做不到）
- Redesk 能管理文件与书籍的关联关系
- Redesk 具备 EPUB 封面自动抽取能力
- Redesk 具备状态变更历史记录

### 1.3 范围限制（已确定）

- 打磨不改变 M1 的功能边界，不新增阅读器/AI 能力
- 允许在书架管理范围内补充体验向功能点
- 允许小幅数据模型调整（如标签颜色、分类图标等字段），不动核心表结构
- 阅读相关入口占位，不实现实际阅读功能

### 1.4 范围破例（v1.1.0 确认）

书籍属性扩充讨论中确认一项破例：**分类拆分触及核心表结构调整**，但在打磨阶段破例执行。理由：

- 当前 `books.category_id` 的建模决策把"客观类型"与"个人用途"两个维度混在一个字段，语义不清，是书架打磨阶段必须厘清的基础问题
- 打磨阶段正是讨论书架属性的时机，顺手把分类语义厘清，避免 M2 之后返工
- 同时新增的 `bookmarks` 表虽属 S2（M2），但遵循"表结构当前即按完整形态设计"原则提前建模，迁移 SQL 现在生成（多一张空表对 SQLite 无成本），M2 只做阅读器交互实现

破例范围严格限定为：books 表新增字段、categories 表加 type 字段、新增 bookmarks 表设计。其余核心表结构（status 五态、owner_id 策略、主题软引用等红线）不动。

## 2. 导入工作流

导入分三种场景，需分别设计。

### 2.1 场景 A：有书籍文件，需要整理成书架

用户已有一批 EPUB/PDF 等书籍文件，需要快速建库。

**流程设想（已确定方向，细节待讨论）：**

1. 批量上传文件到系统
2. 上传后的文件先进入一个**公共临时池**
3. 用户在临时池中看到所有待归属的文件
4. 后续完善书目信息后，由用户将文件与书籍做归属匹配
5. 系统可辅助：自动从文件名提取书名/作者作为匹配建议

**待讨论细节：**
- 临时池的 UI 形态（独立页面？书架上的特殊区域？）
- 从文件名提取元数据的规则与容错
- 已匹配文件是否需要从池中移除
- 临时池是否有容量或时间限制

### 2.2 场景 B：从 Notion 迁移（仅名单，无文件）

用户只有书籍名单（从 Notion 或其他工具导出），需要批量创建书目。

**流程设想（已确定方向，细节待讨论）：**

1. 系统提供**默认 Excel/CSV 导入模板**
2. 用户按模板填写已知清单（书名、作者、ISBN、分类、状态、评分等）
3. 导入模板批量创建书籍条目
4. 如果此前已上传对应的书籍文件（场景 A 的临时池），可快速寻找并匹配

**待讨论细节：**
- 模板包含哪些字段（书名、作者必填，其余可选）
- 导入时的校验策略（部分失败是否全部回滚？逐行跳过？）
- "快速匹配文件"的匹配规则（文件名相似度？手动选择？）
- 是否支持从 Notion 直接导出 CSV 后映射字段（而非手动填入模板）

### 2.3 场景 C：从零开始，逐本添加

用户手动创建单本书籍。

**流程设想（已确定）：**

- 正常创建书籍 → 填写元数据 → 上传文件
- 与现有 M1 功能一致，不需要额外设计
- 优化点：创建流程的步骤精简、链接预填体验提升

## 5. 数据厚度

一本书在系统中的信息丰富度直接影响书架"称手"程度。以下话题已记录，**可能边做边修改**。

### 5.1 已确认新增字段（v1.1.0，详见 §6）

以下字段在 v1.1.0 讨论中确认新增，设计细节见 §6 书籍属性扩充设计：

- `subtitle`（副标题）
- `page_count`（页数，出版物页数）
- `translator`（译者）
- `original_title`（原作名）
- `favorited_at`（收藏时间戳，与 status 正交）
- `genre_category_id`（常规分类，与个人分类拆分）
- `bookmarks` 表（书签，S2 提前建模）

### 5.2 仍待讨论项

- 封面替换（已确定方向）：EPUB 自动抽取的封面不满意时，支持用户手动替换。替换方式需同时支持三种输入渠道：
  - **本地上传**：通过文件选择器选取本地图片
  - **粘贴**：从剪贴板直接粘贴图片（如从网页复制的豆瓣封面）
  - **拖拽**：从本地文件管理器拖拽图片到封面区域
  - 待讨论：三种方式的技术实现方式（前端裁剪/格式转换？后端接收接口？）、替换后是否需要保留原始 EPUB 封面作为回退
- 元数据完整度：缺出版社、缺 ISBN 的书是否在界面上显著标记提醒
- 文件关联状态：有书无文件、有文件无封面等状态是否一眼可见
- 标签颜色：标签是否需要支持颜色/图标以提升视觉区分度
- 分类图标：分类是否需要图标支持
- 阅读痕迹预览：即使不做 M2 阅读器，未来是否能在书架上展示"本书有 3 条高亮"等数据

## 6. 书籍属性扩充设计

> v1.1.0 讨论产出。用户反馈"书籍属性太少，无法满足收纳编辑要求"，将书籍信息分为三类梳理：书籍本身信息、阅读痕迹、主题阅读。本节记录三类的设计决策与新增内容。

### 6.1 三类信息划分

| 类别 | 范围 | 当前状态 |
| --- | --- | --- |
| 第一类：书籍本身信息 | 书名/作者/副标题/常规分类/个人分类/评分/页数/译者/原作名/收藏 | 部分已有，本次扩充 |
| 第二类：阅读痕迹 | 高亮/书签/笔记/标记 | 高亮/笔记/标记模型已设计（S2），书签为本次新增缺口 |
| 第三类：主题阅读 | 书籍关联主题/主题关注问题/同主题书籍 | 模型已完整（P2/M4），本次不动 |

### 6.2 第一类：书籍本身信息 — 新增字段

#### 6.2.1 books 表新增字段

| 字段 | 类型 | 约束 | 说明 | 为后续预留 |
| --- | --- | --- | --- | --- |
| `subtitle` | TEXT | NULL | 副标题 | M3 元数据补全(9.01)可抓取 |
| `page_count` | INTEGER | NULL | 出版物页数（非实际阅读页数） | M5 年度页数目标(5.14) |
| `translator` | TEXT | NULL | 译者 | M3 元数据补全 |
| `original_title` | TEXT | NULL | 原作名 | M3 元数据补全 |
| `favorited_at` | TEXT | NULL | 收藏时间戳，非空即收藏 | M5 概览"最近收藏"、推荐 |
| `genre_category_id` | INTEGER | FK categories NULL | 常规分类（客观类型） | M4 主题按客观类型聚类 |

#### 6.2.2 关键设计决策

**收藏与 status=STORED 正交（已确认）**

- `favorited_at` 是独立二态标记（非空即收藏），与 `status` 完全正交
- 一本书可同时"在读 + 已收藏"或"已读 + 已收藏"
- `status=STORED`（"存"状态）保持原义："存起来不主动读"，是决策记录红线确认的独立业务状态，不动
- 收藏表达"个人珍视/快速找回"语义，STORED 表达"暂不阅读"语义，两者并存不冲突
- 用时间戳而非 0/1 整数：便于"最近收藏"排序，与 `created_at`/`updated_at` 风格一致

**页数语义（已确认）**

- `page_count` 存**出版物标注页数**（书的版权页写的），不是实际阅读页数
- EPUB 页数随字号/屏幕变化，不适合作为固定页数；PDF 页数固定可填
- 实际阅读进度走 `reading_progress.percentage`（S2），与 `page_count` 解耦

**reading_purpose 维持自由文本（已确认）**

- 讨论中曾考虑把 `reading_purpose` 枚举化（精读/浅读/查询/泛读/系统阅读…），最终放弃
- "收藏"原拟作为阅读方式一项，因与 `status=STORED` 重叠，改为独立 `favorited_at` 字段，不进阅读方式枚举
- `reading_purpose` 维持现状：自由文本，用户可填"泛读/精读/参考"等任意文本
- 决策记录"阅读目的表达方式"暂缓项仍保持暂缓，本次不锁定书籍级/任务级

#### 6.2.3 分类拆分（核心表结构破例调整）

**问题**：当前 `books.category_id` 单字段，建模决策 §1 把它定义为"这本书对个人的主要用途/立场（如工作能力提升、文学作品、语言学习）"——这个定义本身把"客观类型"（文学作品）和"个人用途"（工作能力提升）两个维度混在一起。

**方案**：拆分为两个独立分类字段

| 字段 | 语义 | 示例 |
| --- | --- | --- |
| `category_id`（现有，重定义） | 个人分类：对个人的用途/能力/需求 | 提升领导力、研究素材、休闲读物 |
| `genre_category_id`（新增） | 常规分类：书籍客观类型 | 小说、技术、历史、哲学 |

**categories 表方案**：不建两套表，给现有 `categories` 表加 `type` 字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `type` | TEXT | NOT NULL DEFAULT 'PERSONAL'，取值 `GENRE`（常规分类）/ `PERSONAL`（个人分类） |

约束：`(owner_id, name, type)` 唯一（原 `(owner_id, name)` 唯一调整为三元组）。

**方案理由**：
- 复用现有 categories CRUD，不新增表
- 迁移简单：现有数据全标为 `PERSONAL`，`category_id` 语义不变
- 模型更简，两池分类按 type 区分
- 常规分类仍遵循决策记录"用户自定义，不内置通用类型树"——不预置基础树，用户自建

**三个组织维度的职责区分**（避免用户困惑"该填哪个"）：

| 维度 | 字段 | 基数 | 语义 |
| --- | --- | --- | --- |
| 常规分类 | `genre_category_id` | 一书一类 | 书的客观类型 |
| 个人分类 | `category_id` | 一书一类 | 对个人的主要用途 |
| 标签 | `book_tags` | 一书多标 | 任意自由标记（多对多） |

### 6.3 第二类：阅读痕迹 — 新增 bookmarks 表

#### 6.3.1 缺口识别

当前阅读痕迹层只有：`reading_progress`（一本书一条"上次读到哪"）+ `highlights`（选一段文字）+ `notes`。**没有独立的"书签"概念**——标记一个位置点（不选中文字）、一本书可多条、用于快速跳转。epub.js 原生支持书签，这是 S2 的真实缺口。

#### 6.3.2 bookmarks 表设计（S2 提前建模，M2 实现）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | PK AUTO | |
| book_id | INTEGER | NOT NULL FK books | |
| owner_id | INTEGER | NOT NULL FK users | |
| cfi | TEXT | NOT NULL | epub.js CFI 位置 |
| label | TEXT | NULL | 书签标题/备注 |
| percentage | REAL | NULL | 进度百分比（展示用） |
| created_at | TEXT | NOT NULL | |

约束：`(book_id, owner_id, cfi)` 唯一。

**设计要点**：
- 与 highlights 共享 CFI 体系，M2 跳回原文逻辑(3.15/3.16)可复用
- schema 文件现在写好，迁移 SQL 现在生成（多一张空表对 SQLite 无成本）
- 阅读器交互（添加/删除/跳转书签）留到 M2 实现
- 遵循《数据模型》"表结构当前即按完整形态设计"原则，避免 M2 临场建模

#### 6.3.3 阅读痕迹层完整模型（S2 全景）

| 表 | 用途 | 状态 |
| --- | --- | --- |
| `reading_progress` | 一书一条上次阅读位置 | 模型已设计（S2） |
| `highlights` | 选段文字高亮/划线 + 附注 + 标记 | 模型已设计（S2） |
| `notes` | 独立笔记（TipTap 富文本） | 模型已设计（S2） |
| `bookmarks` | 位置点书签，快速跳转 | **本次新增模型设计** |

### 6.4 第三类：主题阅读 — 无改动

模型已完整，本次不动：

| 你列的需求 | 承载表 | 阶段 |
| --- | --- | --- |
| 书籍跟哪个主题相关 | `topic_books`（多对多） | P2/M4 |
| 主题关注什么问题 | `topic_entries`（entry_type=QUESTION） | P2/M4 |
| 同主题下还有哪些书 | `topic_books` 反查 | P2/M4 |

阶段说明：`topics`/`topic_books` 等表标注为 P2（M4），当前未迁移。打磨阶段不动主题表，等 M4 落地。主题"最小字段"在决策记录里是暂缓项，本次不锁。

### 6.5 实施约束

- **不动的东西**：status 五态、STORED 红线、owner_id 策略、主题软引用、reading_purpose 字段、主题相关表

## 7. 标准书籍管理流程细化

> v1.2.0 讨论产出。基于使用逻辑（添加 → 上传 → 查询 → 编辑）梳理标准创建流程的细节决策。本节聚焦**标准创建**（人工操作），AI 创建见 §8。

### 7.1 添加书籍

#### 7.1.1 元数据录入方式与 source_url

- **手动填写**：当前唯一方式，确认无问题
- **链接预填**：NeoDB/豆瓣链接自动抓取功能暂不实现（功能清单 1.03/1.04 已列，M1 未落地，留待后续）
- **新增字段 `source_url`**：书籍介绍链接，用户可填写豆瓣/NeoDB 等页面 URL
  - 与现有 `metadata_source`（manual/neodb/douban 枚举）配合：metadata_source 标记来源类型，source_url 存具体链接
  - 字段定义见 §6.6

#### 7.1.2 必填字段调整

- **只书名必填**：`title` 保持 NOT NULL
- **作者改为可选**：`author` 从 NOT NULL 改为 NULL（核心表约束破例调整）
  - 理由：AI agent 或快速收录时可能只知道书名；录入时间紧迫时先建条目再补
  - 前端展示：作者留空时显示"未知作者"
  - 字段定义见 §6.6

#### 7.1.3 创建时重复检测

- **确认要做**：创建书籍时自动触发重复检测（复用现有 LCS 算法，默认阈值 0.6）
- 行为待定（二选一，见 §9 待讨论项）：
  - A. 重复则拒绝创建，返回已存在的 book_id（严格）
  - B. 重复则提示但允许继续创建（宽松）

#### 7.1.4 创建时传文件（可选）

- **支持一步完成**：创建书籍时可选带文件，一步完成"建书 + 传文件"
- 实现方式待定：`POST /books` 支持 multipart（元数据字段 + 可选文件），或新增 `POST /books/with-file` 端点
- AI 创建不需要传文件（见 §8.3.3）

### 7.2 上传文件

#### 7.2.1 确认事项

- **不支持 URL 代下载**：不提供"传 URL 后端下载"功能
- **文件去重**：上传时用 checksum（SHA256）校验
  - 当前 `book_files.checksum` 已存但未用于去重，需补校验逻辑
  - 行为：同一 book 下同 checksum 文件拒绝上传；不同 book 下同 checksum 文件提示但不拦截

#### 7.2.2 临时文件池

- **新增功能**：未关联书籍的文件可先入临时池，后续匹配归属
  - 对应 §2.1 场景 A（先有文件后建书）
  - 需要新增"未关联文件"存储区或标记机制
  - UI 形态待讨论（见 §9）

#### 7.2.3 书库文件视图

- **新增入口**：以已上传的书籍文件为核心展示内容
  - 视图维度：以文件列表为主，展示文件格式/大小/关联书籍/上传时间
  - 用途：快速查看书库已有哪些文件、哪些文件未关联书籍、文件格式分布
  - 与书架视图（以书籍为核心）互补

### 7.3 查询

#### 7.3.1 筛选维度扩展

在现有筛选（`q`/`status`/`category_id`/`tag_id`/`visibility`/`in_trash`）基础上新增：

| 筛选参数 | 说明 | 阶段 |
| --- | --- | --- |
| `favorited` | 按收藏筛选（true/false） | 打磨阶段 |
| `genre_category_id` | 按常规分类筛选 | 打磨阶段 |
| `has_files` | 按文件有无筛选（true/false），找出"有书无文件"的书 | 打磨阶段 |
| `topic_id` | 按关联主题筛选 | M4 落地后激活，当前预留 |

#### 7.3.2 搜索范围

- 当前 FTS5 只索引 title/author/isbn
- 扩充属性后是否将副标题/译者/原作名纳入 FTS5：待讨论（见 §9）

#### 7.3.3 批量操作补充

在现有批量操作（`set_status`/`set_category`/`set_tags`/`set_visibility`/`delete`）基础上新增：

| 批量操作 | 说明 |
| --- | --- |
| `set_favorited` | 批量设收藏/取消收藏 |
| `set_genre_category` | 批量设常规分类 |

### 7.4 编辑属性

#### 7.4.1 收藏专用端点

- `POST /books/:id/favorite`：收藏（设置 `favorited_at`）
- `DELETE /books/:id/favorite`：取消收藏（置空 `favorited_at`）
- 比 PATCH 更语义化，前端按钮直接调用

#### 7.4.2 阅读时间字段（新增）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `started_at` | TEXT NULL | 开始读时间 |
| `finished_at` | TEXT NULL | 读完时间 |

- **自动填充**：status 变为 READING 时自动填 `started_at`（若为空）；变为 READ 时自动填 `finished_at`（若为空）
- **手动修改**：两个字段均支持用户手动修改（覆盖自动填充值）
- **录入时间**：现有 `created_at` 即录入时间，无需新增字段
- 字段定义见 §6.6

#### 7.4.3 字段审计范围（建议）

- **记历史**：status 变更（现有 status_history）+ `started_at`/`finished_at` 变更
- **不记历史**：评分、分类、标签、收藏、自定义属性等字段变更不记历史
- 理由：避免过度设计；状态与阅读时间是阅读进度关键节点，值得追溯；其余字段变更频率低且可从 `updated_at` 推断

#### 7.4.4 并发编辑

- **不做乐观锁**：last-write-wins（最后写入覆盖）
- 理由：单用户场景下不会同时修改一本书；外部 AI agent 受限不能编辑（见 §8.3），无并发风险

## 8. AI Agent 接入设计

> v1.2.0 讨论产出。开放 API 给 AI agent 添加/查询书籍的设计。Redesk 的 AI 分两种模式，权限边界不同。

### 8.1 两种 AI 模式

| 模式 | 定位 | 权限 | 落地阶段 |
| --- | --- | --- | --- |
| 系统内置 AI | 走 `AIService` 接口，系统配置 LLM key | 较大（元数据补全/摘要/标签建议等读写） | M3 |
| 外部 Agent AI | 通过 skill 或连接方式接入的远程替身 | 只读 + 创建，不能编辑已有信息 | 打磨阶段（本文档） |

本节聚焦**外部 Agent AI**。系统内置 AI 见 M3 执行项。

#### 8.1.1 外部 Agent AI 定位

- **场景**：用户不方便操作应用时，通过外部 agent 远程添加书籍或查询书库
- **核心原则**：减少风险，以添加和查询为主，不能远程编辑已有信息
- **不允许的操作**：编辑已有书籍、删除书籍、上传文件、修改设置/用户、批量删除

### 8.2 API Token 鉴权

#### 8.2.1 当前鉴权现状

- 现有鉴权只有 session cookie 一种（单用户模式自动 admin，多用户模式需登录）
- **没有 API token / API key 机制**——AI agent 无法用 cookie 之外方式鉴权
- 这是开放给 agent 的前置条件，必须新增

#### 8.2.2 api_tokens 表设计

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | PK AUTO | |
| owner_id | INTEGER | NOT NULL FK users | |
| name | TEXT | NOT NULL | 备注（如"我的 Agent"） |
| token_hash | TEXT | NOT NULL | token 哈希（不存明文） |
| scopes | TEXT | NOT NULL | 权限范围，逗号分隔 |
| last_used_at | TEXT | NULL | 最近使用时间 |
| created_at | TEXT | NOT NULL | |
| revoked_at | TEXT | NULL | 吊销时间，非空即已吊销 |

- token 格式：`rdk_<随机串>`，生成时只显示一次明文
- 鉴权方式：`Authorization: Bearer rdk_xxxx`
- 兼容现有 session cookie：两条鉴权路径并存，中间件优先查 Bearer token，回退到 session

#### 8.2.3 Token 管理

- 设置页：生成（显示一次明文）、查看列表（只显示 name/last_used_at/scopes，不显示明文）、吊销
- token 绑定 owner_id，继承该用户的数据边界
- 吊销后立即失效

### 8.3 外部 Agent 权限边界

#### 8.3.1 Scope 设计

| Scope | 允许操作 | 禁止操作 |
| --- | --- | --- |
| `books:read` | GET /books、GET /books/:id、GET /categories、GET /tags | — |
| `books:create` | POST /books（创建新书） | 编辑已有、删除 |
| —（不授予） | — | PATCH /books/:id、DELETE /books/:id |
| —（不授予） | — | 文件相关端点（POST /books/:id/files 等） |
| —（不授予） | — | 设置/用户管理端点 |
| —（不授予） | — | 批量删除 |

#### 8.3.2 外部 Agent 默认权限

- 默认 scope：`books:read` + `books:create`
- 不授予编辑/删除/文件/设置相关 scope
- 这意味着外部 agent **只能创建新书和查询，不能改动已有数据**
- 系统内置 AI（M3）不通过 token 鉴权，走内部 `AIService` 接口，权限由 M3 定义

#### 8.3.3 安全限制

- **速率限制**：按 token 计数，限制请求频率（具体阈值待定，见 §9）
- **审计日志**：token 发起的操作记录日志（token_id + 操作 + 时间 + 资源），便于追溯 agent 行为
- **不允许传文件**：外部 agent 无文件上传权限（无 `files:write` scope），减少存储风险
- **创建时强制重复检测**：外部 agent 创建书籍时强制开启重复检测（避免 agent 批量加重复书）

### 8.4 Agent 友好端点

#### 8.4.1 创建端点适配

- `POST /books` 对 agent 够用，但需适配：
  - 支持只传 title（作者可选，见 §7.1.2）
  - 强制重复检测（agent 场景，见 §8.3.3）
  - 返回完整 book 对象（含 id），便于 agent 后续查询

#### 8.4.2 查询端点

- 现有 GET /books 及筛选参数对 agent 友好，无需额外改造
- 字段补充后（subtitle/translator/source_url 等）响应自动包含

#### 8.4.3 待定项

- 是否提供 OpenAPI/Swagger schema 供 agent 自动发现接口：待讨论（见 §9）
- 是否新增 `POST /books/batch-create` 批量创建：待讨论（见 §9）
