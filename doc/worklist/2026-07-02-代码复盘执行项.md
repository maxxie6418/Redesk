## WL-001 系统维护接口权限收口

- 优先级：P1
- 类型：安全 / 权限边界
- 背景：
  - 当前系统维护型接口权限不一致。
  - `POST /system/clear-cache` 未做登录校验。
  - `POST /system/reset` 只校验当前用户密码，未校验管理员身份。
  - `POST /system/backup`、`POST /system/fts-rebuild` 也只有登录校验，没有管理员限制。
- 目标：
  - 所有系统维护型接口统一收口到“仅管理员可执行”。
  - 未登录与普通用户访问时返回一致且明确的错误。
- 涉及文件：
  - `apps/api/src/routes/system.ts`
  - `apps/api/src/lib/auth.ts`
  - 如有必要：`packages/shared/src/errors.ts`
- 建议动作：
  - 增加管理员校验工具函数，例如 `requireAdminUserId(req)`。
  - 将 `/system/stats`、`/system/storage`、`/system/backup`、`/system/fts-rebuild`、`/system/clear-cache`、`/system/reset` 的权限规则明确化。
  - 明确哪些系统接口允许普通登录用户访问，哪些必须管理员访问，不要仅靠前端隐藏入口。
  - 如接口契约变化，需要同步 `doc/API接口.md`。
- 验收标准：
  - 未登录访问上述接口返回 401 或既定未授权错误。
  - 普通用户访问管理员接口返回 403 或既定无权限错误。
  - 管理员访问行为保持正常。
  - 前端设置页无功能回归。

## WL-002 修正书籍文件上传默认覆盖主文件的问题

- 优先级：P2
- 类型：业务逻辑 / 文件管理
- 背景：
  - 当前关联到书籍的文件上传会默认把新文件设为主文件。
  - 这会导致一书多文件场景下，用户已有主阅读文件被新上传文件自动替换。
  - 前端 hook 已经预留 `isPrimary` 参数，但后端当前没有按该参数执行。
- 目标：
  - 上传书籍文件时，是否设为主文件应由前端显式控制。
  - 默认行为需符合当前产品语义，不得无条件覆盖现有主文件。
- 涉及文件：
  - `apps/api/src/routes/files.ts`
  - `apps/web/src/hooks/use-files.ts`
  - 如有相关入口：书籍详情文件上传 UI
  - 如有必要：`packages/shared/src/schemas.ts`
- 建议动作：
  - 后端读取 multipart 中的 `is_primary` 字段。
  - 明确默认策略：
    - 该书还没有主文件时，可自动设为主文件。
    - 已有主文件时，只有显式传入 `is_primary=true` 才替换。
  - 检查未关联文件匹配到书籍时是否也存在类似主文件覆盖问题。
  - 如行为变更，需要同步接口文档。
- 验收标准：
  - 已有主文件的书再上传普通文件，不会自动覆盖主文件。
  - 显式指定主文件时，旧主文件会被正确降级。
  - 首次上传文件的书仍能正常得到主文件。
  - 文件列表、书籍详情页显示与实际状态一致。

## WL-003 清理或补齐失效的文件替换接口

- 优先级：P3
- 类型：接口一致性 / 技术债
- 背景：
  - 前端仍保留 `useReplaceFile()`，请求 `POST /books/:id/files/:fileId/replace`。
  - 后端当前没有对应路由，后续一旦接入此能力会直接 404。
  - 这属于“前端遗留契约”和“后端真实契约”不一致。
- 目标：
  - 决定该能力是继续支持，还是彻底删除遗留代码。
  - 保证前后端关于“替换文件”的契约唯一且真实。
- 涉及文件：
  - `apps/web/src/hooks/use-files.ts`
  - `apps/api/src/routes/files.ts`
  - 相关调用点搜索 `useReplaceFile`
  - `doc/API接口.md`
- 建议动作：
  - 先确认产品是否仍需要“替换文件内容但保留记录”的能力。
  - 若需要：
    - 后端补齐真实替换接口。
    - 前端接入并验证详情页/文件库实际可用。
  - 若不需要：
    - 删除 `useReplaceFile()` 及相关死代码。
    - 避免后续误用。
- 验收标准：
  - 仓库中不存在“前端调用但后端没有”的替换接口。
  - 文档、前端 hooks、后端 routes 三者一致。

## WL-004 同步 M2 阶段文档与当前实现现状

- 优先级：P3
- 类型：文档一致性 / 阶段边界
- 背景：
  - 代码里已经存在真实的 EPUB 阅读页和可点击入口。
  - 但书架卡片、部分说明和阶段表述仍把阅读器当作“尚未开始”或“仅占位”。
  - 这会误导后续 AI 对当前实现成熟度的判断。
- 目标：
  - 把“当前已实现到什么程度”写清楚。
  - 明确区分：
    - 已有基础阅读器壳
    - 尚未完成阅读留痕、进度、高亮、笔记体系
- 涉及文件：
  - `doc/开发执行计划.md`
  - `doc/技术方案.md`
  - 如需：`doc/Redesk-功能清单-v1.1.md`
  - 如需：前端页面中的提示文案
- 建议动作：
  - 将 M2 状态描述改为“基础阅读页已出现，但核心留痕能力未闭环”之类的真实表述。
  - 检查书架卡片、详情抽屉、阅读相关占位页中的文案是否一致。
  - 保持“不夸大已完成度”，但也不要继续把已落地能力写成完全未开始。
- 验收标准：
  - 主要产品/开发文档对阅读器现状表述一致。
  - 前端提示文案不再与真实实现冲突。

## WL-005 统一页面外壳并收紧 Sidebar 的职责

- 优先级：P3
- 类型：结构规整 / 可维护性
- 背景：
  - 大部分页面已使用 `AppShell`。
  - 设置页仍直接拼接 `AppSidebar`，形成第二套布局写法。
  - `AppSidebar` 组件虽然接收 `user`，但内部又自行请求认证状态与初始化状态，职责过重。
- 目标：
  - 统一“页面壳层”的使用方式。
  - 让 `AppSidebar` 更偏展示和交互，不再承担过多认证查询逻辑。
- 涉及文件：
  - `apps/web/src/components/app-shell.tsx`
  - `apps/web/src/components/app-sidebar.tsx`
  - `apps/web/src/routes/settings.tsx`
  - `apps/web/src/routes/overview.tsx`
  - `apps/web/src/routes/file-library.tsx`
  - `apps/web/src/routes/reading-notes.tsx`
  - `apps/web/src/routes/reading-topics.tsx`
- 建议动作：
  - 让设置页也改走 `AppShell`，避免继续分叉。
  - 评估是否把 `useCurrentUser()` / `useAuthInit()` 上提到壳层或路由层。
  - 明确 `AppSidebar` 的输入：导航激活项、搜索值、统计数据、登录态展示数据。
  - 不要在这项里顺手改登录策略本身，只处理结构收口。
- 验收标准：
  - 主要后台页面使用一致的壳层模式。
  - `AppSidebar` 的职责更单一，重复认证查询减少。
  - 页面视觉与行为无回归。

## WL-006 拆分前端超大文件，先从设置页和书籍详情开始

- 优先级：P3
- 类型：结构规整 / 维护成本
- 背景：
  - `bookshelf.tsx`、`settings.tsx`、`book-detail-sheet.tsx` 体量已经过大。
  - 当前还能维护，但继续叠加 M2/M3 能力会明显增大改动风险。
- 目标：
  - 在不改业务行为的前提下，把大文件拆成更稳定的模块。
  - 为后续 M2 阅读留痕和 M3 AI 能力接入预留清晰位置。
- 涉及文件：
  - `apps/web/src/routes/settings.tsx`
  - `apps/web/src/components/book-detail-sheet.tsx`
  - `apps/web/src/routes/bookshelf.tsx`
- 建议动作：
  - 第一阶段优先拆：
    - 设置页各 Tab
    - 书籍详情的档案区 / 封面区 / 文件区 / 占位区
  - 第二阶段再考虑拆书架卡片视图与导入弹窗。
  - 拆分时保持 props 边界清晰，避免把状态四散复制。
- 验收标准：
  - 页面行为不变。
  - 单文件体量明显下降。
  - 新结构能让后续功能更容易定位落点。
