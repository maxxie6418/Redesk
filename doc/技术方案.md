## 2. 技术路线选型

### 2.1 候选路线对比

| 维度 | Route A：全栈 TypeScript（选定） | Route B：Python 后端 + React | Route C：Go 后端 + React |
| --- | --- | --- | --- |
| 后端 | Node 20 + Fastify + better-sqlite3 + Drizzle | FastAPI + SQLAlchemy + SQLite | Go (Chi/Echo) + sqlc + SQLite |
| 前端 | Vite + React + TypeScript（三者相同） | 同左 | 同左 |
| AI/RAG | 直连 LLM SDK + sqlite-vec 检索 | LangChain/LlamaIndex，生态最强 | 生态最弱，AI 多半需挂边车 |
| 语言统一度 | 前后端一种语言、共享类型 | 两套语言、类型需重维护 | 两套语言 |
| 自托管运维 | 一进程一镜像 | 一镜像，稍重 | 单二进制，最省 |
| 与 epub.js 契合 | 同生态，天然配套 | 一般 | 一般 |
| AI 深度扩展潜力 | 中（够用，需自建检索层） | 最强 | 弱 |
| 功能覆盖 | 功能清单 1–11 无一项被卡住 | 同 | 同 |

### 2.2 选定路线：Route A（全栈 TypeScript，暂定）

经通读功能清单 1–11 与全部决策记录，选定 Route A。理由不是"技术本身最优"，而是最匹配本项目特征：工程体量大头是 Web 管理 + 文件管理 + epub.js 阅读器 + OPDS + 导出，AI 是增强层且分阶段引入；一种语言贯穿全栈对维护者认知负担最低；epub.js 本属 JS 生态，天然配套。

### 2.3 选型理由（功能 + 代价 + 可补救性）

- **功能支撑**：Route A 不阻塞功能清单任何一项；阅读器（技术风险最集中处）因同生态有更多现成方案，做稳概率更高。
- **开发代价**：一种语言降低长期维护成本；数据层用单一 SQLite 文件 + 内置全文检索 + 向量检索，部署简单、备份即复制文件，契合数据主权。
- **可补救性（决定性因素）**：当前 AI 最终形态未定型（决策记录多处暂缓），"选错好不好补救"比"理论最优"更重要。
  - 选 A，日后发现 AI 是重心 → 加 Python 边车即可，主应用不动，补救成本最低。
  - 选 B，日后发现阅读器/界面才是大头 → 两套语言长期维护，补救成本高。
  - 选 C，日后 AI 要做深 → 仍需挂边车，补救成本中高。

### 2.4 让步与对冲

- **让步**：AI 深度生态不如 Python；不如 Go 省资源；AI 不像 Python 开箱即用。
- **对冲**：所有 AI 能力收在 `AIService` 接口后，provider/模型/检索实现可替换；必要时加 Python RAG 边车，主应用不受影响。

## 3. 技术栈总览

### 3.1 后端

- 运行时：Node.js 22 LTS + TypeScript 5。
- Web 框架：Fastify（高性能、内置 schema 校验、插件体系，适合 OPDS / 文件流式 / AI SSE 三类端点）。
- 数据库访问：better-sqlite3（同步、极快、API 简单）+ Drizzle ORM（TS 优先、类型与 Zod 对齐、SQL 友好）+ Drizzle Kit 迁移。
- 检索：SQLite FTS5（书名/作者/ISBN/笔记全文检索）；sqlite-vec（AI 向量检索，复用同一 SQLite 文件，不另起服务）。
- 鉴权：会话 + Cookie；由 `settings` 表中 `multi_user` 键动态控制——关闭时单用户免登录（自动以默认管理员身份操作），开启时需密码登录；数据带 `owner_id` 预留多用户。
- 文件：本地挂载卷或 S3 兼容对象存储；支持 `local_only` / `cloud_only` / `dual` 三态存储策略，写入按 `primary_location` 落盘，`dual` 另一端标记为 `pending` 待同步；范围请求端点；EPUB 封面抽取缓存。
- OPDS：Fastify 路由输出 Atom XML（OPDS 1.2）。

### 3.2 前端

- 框架：Vite + React 18 + TypeScript（阅读器重客户端交互，SPA 给 epub.js 最大控制权；个人应用无 SEO 需求，不上 SSR）。
- UI 组件：shadcn/ui（与现有设计稿的暖色编辑风、terra-cotta #C96442、纸感底色、Newsreader/Poppins/Lora 契合，可深度主题化）。
- 阅读器：epub.js，CFI 锚定阅读位置与高亮。
- 笔记编辑：TipTap（ProseMirror），可序列化 Markdown（备选 Milkdown）。
- 图表：Recharts + cal-heatmap（阅读档案统计与热力图）。
- 数据/路由：TanStack Query + React Router。

### 3.3 数据与存储

- 主存储：单一 SQLite 文件；书籍文件存本地磁盘，数据库记路径/格式/大小/校验值。
- 用户拥有的根实体带 `owner_id`（当前单账户无感，预留 ≤5 人轻量隔离）；从属关系表通过父表继承归属，查询与写入时校验 owner 边界。
- 软删除用 `deleted_at`；`存` 为独立状态值，不复用删除路径。
- 自定义收藏属性用弹性字段（JSON 列）承载，避免频繁改表。

### 3.4 AI

- 接入：可配置 LLM provider（8.08），结构化 prompt，SSE 流式输出。
- 检索：阶段二引入嵌入 + sqlite-vec；嵌入用外部 embedding API，用户自带 key。
- 隔离：`AIService` 接口收敛所有 AI 能力，可换 provider/模型/检索实现，可加 Python 边车；API key 读取和日志脱敏遵循配置安全规则。
- 依据：回答标注引用的书 + 章节，阶段二细化到高亮/笔记。

### 3.5 部署与集成

- 部署：自托管 Docker，多阶段镜像 + docker-compose（服务 + 数据卷）。NAS / VPS / 家用服务器均可；公网可选反向代理上 HTTPS。
- 云同步：优先内置 S3 兼容对象存储同步（阿里云 OSS / AWS S3 / Cloudflare R2 / MinIO / B2），用户在设置页填 endpoint/bucket/key/secret；只同步书籍文件 + SQLite 备份副本，不同步在线 DB。rclone / Google Drive / Dropbox 后置为可选项。
- OPDS：1.2 协议输出，供 KOReader 等阅读器订阅/搜索/下载，带基础认证。
- 备份：容器内定时任务用 `VACUUM INTO` 生成干净副本，保留最近 N 份。

### 3.6 工程结构

```
redesk/
  apps/
    web/        # Vite + React SPA
    api/        # Fastify 后端
  packages/
    shared/     # 类型、Zod schema、常量（前后端共享）
    db/         # Drizzle schema + 迁移
  docker-compose.yml
  Dockerfile
```

pnpm monorepo 管理，前后端共享类型包。

## 4. 分块设计

### 4.1 书架与数据基础

- **做什么**：把"一本书"及其属性、文件、状态变成可长期管理、可检索、可导出的稳定结构。
- **支撑功能**：§1 书架管理（1.01–1.31）、§2 文件管理（2.01–2.10）、§9 状态体系、可见性基础（1.23）、回收站（1.25）。
- **怎么落地**：
  - 元数据：录入只要求书名 + 作者必填，其余（ISBN、出版社、简介、封面等）可选；自定义属性走弹性字段。支持手动录入与 NeoDB/豆瓣链接自动回填，失败可手动补齐。
  - 一书多文件：可挂多个文件，标一个主阅读文件；文件本体存磁盘，数据库记元信息；封面从 EPUB 抽取缓存。
  - 状态体系：`收录 / 计划读 / 在读 / 已读 / 存`，`存` 为独立状态值，与删除/归档不同路径；状态变更记时间轴。
  - 回收站：删除走软删除（`deleted_at`），保留期可配置，支持恢复或彻底清空。
  - 分类/标签：分类层级或平级；标签多对多；可主动建书与书关联；规则版重复检测。
  - 检索：Step 1 做书名/作者/ISBN FTS5；Step 2 在笔记/高亮产生后激活笔记与高亮检索；多条件筛选、排序、分页、批量操作。
  - 预留：根实体带 `owner_id`，从属表通过父表继承归属。
- **开发代价**：中等，地基块，表结构尽量一次定好。元数据自动抓取是最费时单项。
- **风险与对策**：抓取依赖第三方页面结构 → 优先 NeoDB 开放 API + 失败兜底手动补齐；弹性字段复杂筛选受限 → 高频项再升级为正式列；重复检测误报 → 规则版先上，AI 增强版后续补充。
- **检索分层（已确认）**：
  - 层 1（Step 1 做）：书名/作者/ISBN 检索，短文本，毫秒级，成本低。
  - 层 1b（Step 2 激活）：笔记/高亮检索，依赖阅读器与笔记表产出数据。
  - 层 2（整本书正文检索，对应 3.25，延后）：属增强/待定位，单本书内范围；FTS5 对百万字书查询仍毫秒级，成本在导入时抽取正文建索引，非查询性能。

### 4.2 阅读器与笔记沉淀

- **做什么**：阅读时产生的高亮、划线、笔记、进度稳定保存、随时回看、跳回原文。定位为数据生产入口，阅读器非主目标。
- **支撑功能**：§3 核心 3.01–3.20（3.20 并入 4.1 层 1）。增强项 3.21–3.31 预留接口、暂不实现，待定位确认后排期。
- **怎么落地**：
  - 打开与翻阅：epub.js 渲染、目录、翻页、进度。
  - 阅读位置：CFI 记录，关闭存、重开恢复。
  - 高亮/划线：选中文字标记 + 存 CFI 范围 + 存原文文字兜底；重开按 CFI 重画。
  - 附注：高亮上挂批注，可增删改、点击查看。
  - 独立笔记：不绑高亮，属某本书，富文本可导出 Markdown。
  - 跳回原文：笔记/高亮列表点击 → 阅读器定位到 CFI。
  - 标记体系：高亮/笔记可打重要/疑问/启发等标签，预留扩展。
  - 单书阅读痕迹：汇总该书高亮/笔记/进度。
- **开发代价**：高，全项目技术风险最集中。epub.js 高亮持久化与重开重画需专门验证。
- **风险与对策**：CFI 漂移 → 存原文文字兜底锚点；EPUB 格式参差 → 解析容错 + 失败提示；DRM → 明确仅支持无 DRM 文件；大部头卡顿 → epub.js 按章分块加载；增强项定位未定 → 预留接口不提前做。

### 4.3 主题阅读

- **做什么**：`主题` 为独立对象，把跨书阅读材料重新组织，用于主题式深读与比较。
- **支撑功能**：§4 主题阅读 4.01–4.17。
- **怎么落地**：
  - 主题为独立对象（名称 + 说明 + 内容区），非标签；可从一书发起、多书抽象、空主题后补。
  - 书与主题多对多。
  - 核心原则：主题"引用"而非"拥有"阅读痕迹——高亮/笔记/章节片段仍归原书，主题只组织；主题删除走软删除，仅隐藏主题及其引用，不删原始数据；原始痕迹物理删除时主题侧引用自动摘除。
  - 主题自有沉淀：待探索问题、阶段性判断、多书比较结论。
  - 主题内汇总与检索；章节片段关联复用 CFI 机制。
- **开发代价**：中。难点在守住"引用而非拥有"边界。工作区深化（4.16 / 10.03）为长期演进项，当前只搭基础结构。
- **风险与对策**：引用关系混乱 → 主题软删除 + 引用表保留 + 原痕删除时自动摘除；主题字段最小集未定 → 先最小集 + 弹性字段；工作区深化为后续 → 预留不提前实现。

### 4.4 导出、备份与数据主权

- **做什么**：让用户随时能完整带走数据，产品可信度底线。
- **支撑功能**：§6 导出与备份 6.01–6.11。
- **怎么落地**：
  - 元数据导出 JSON/CSV（单本/多本/全书架）。
  - 笔记/高亮/标记导出 Markdown（人读）+ JSON（机读），一书一文件，通用格式不依赖专有结构。
  - 文件下载单个/批量打包，断点续传。
  - 手动全量备份一键 ZIP（DB + 原始文件 + Markdown）。
  - 自动备份定时 `VACUUM INTO`，保留 N 份，本地为主，不默认强依赖云端。
  - 笔记自动落盘：每次变更异步重写该书 Markdown 备份。
  - 导入外部笔记：解析 Notion/Obsidian Markdown，按书名模糊匹配，低置信度手动确认。
  - AI 派生内容单独导出/隔离，不与用户原始内容混。
- **开发代价**：中低。导出本质读出写文件，无技术难点；早期定稳定格式后一劳永逸。
- **风险与对策**：格式变动破坏旧备份 → 带版本号、向后兼容；自动备份吃磁盘 → 限保留份数；导入匹配错书 → 置信度 + 手动确认。

### 4.5 部署、鉴权与第三方集成

- **做什么**：把 Redesk 跑起来、安全对外、与阅读器/云盘打通。
- **支撑功能**：§8 第三方集成（8.01–8.08）、§7 可见性与权限（当前仅 1.23，其余预留）、部署形态。
- **怎么落地**：
  - 自托管 Docker，数据卷挂载，重建容器数据不丢；公网可选反向代理 + HTTPS。
  - OPDS 1.2 输出供 KOReader 等订阅/搜索/下载，按状态/标签筛选，带基础认证。
  - 云同步：优先应用内置 S3 兼容对象存储同步，用户填配置即用；只同步文件层 + 备份副本。rclone / Google Drive / Dropbox 后置可选，面向已有同步链路的高级用户。
  - 鉴权：因 OPDS 对外，起步带登录（账号密码 + 会话）；鉴权模式由 `multi_user` 设置键控制——关闭时为单用户免登录自动管理员、开启时为多用户密码登录；根实体 `owner_id` 已埋，日后开 ≤5 人是加登录页和查询约束而非重构数据层；OPDS 复用同账户基础认证。
  - 可见性：当前仅每本书公开/私有（1.23）；§7 细粒度权限声明预留，数据层留 `owner_id` + `visibility` 扩展位。
  - TTS/AI 接入配置（8.07/8.08）为配置入口，AI 功能见 4.6，TTS 属增强待定位。
  - 配置安全：LLM / OSS / rclone 等 secret 只保存在本地配置或数据库加密字段中，返回 API 时脱敏；日志、导出、错误响应不得输出明文密钥。M1 设置页可先保存配置，测试连接与同步任务按对应阶段实现。
- **开发代价**：中。Docker 打包 + OPDS 为主，内置 S3 同步作为优先路径降低默认配置复杂度；rclone 作为可选路径后置；鉴权轻量起步。
- **风险与对策**：OPDS 暴露 → 起步带鉴权不裸奔；公网被扫描 → 反向代理 + HTTPS 或仅局域网；S3 同步配置错误 → 校验 + 测试连接；多用户演进 → 字段已预留。

### 4.6 AI 能力（分阶段）

- **做什么**：AI 为增强层，逐步成为基于个人阅读经历的陪读助手与辅助思考者；回答有依据可追溯、生成内容与用户原始内容分开、读取范围未来分级控制。
- **支撑功能**：§9 AI 能力 9.01–9.18（8.08 接入配置见 4.5）。
- **怎么落地（三阶段）**：
  - 阶段一（管理辅助 + 阅读辅助）：录入辅助（9.01–9.04）、阅读辅助（9.05–9.08），直接调外部 LLM，结果带引用（书 + 章节，9.16），存为 AI 派生资产并与用户内容隔离（9.14/9.15）。无新基础设施。
  - 阶段二（书库级知识利用）：RAG"开卷考试"——嵌入高亮/笔记/章节片段存 sqlite-vec，提问语义检索相关片段拼 prompt，基于个人书库回答（9.13）+ 主题分析（9.09–9.12），引用细化到高亮/笔记（9.17）。
  - 阶段三（分级访问）：检索层按保密等级过滤 AI 可读范围（9.18）。
  - 全部收在 `AIService` 接口后，可换 provider/模型/检索实现，可加 Python 边车；密钥读取和日志脱敏遵循 4.5 配置安全规则。
- **开发代价**：阶段一中（提问工程 + 结果隔离）；阶段二中高（嵌入 + 检索质量调优）；阶段三中（权限过滤接入检索层）。按阶段渐进。
- **风险与对策**：幻觉/引用不实 → 强制基于检索片段 + 引用对应真实片段 + 标注"AI 生成"；生态不够用 → 接口隔离 + Python 边车；调用成本 → 用户自带 key + 缓存嵌入 + 批量处理；分级访问未定型 → 阶段三细化，先留可见性字段。

## 5. 分期建议

遵循《需求总纲》§13 阶段推进原则：基础资产模型稳定、数据可留存可导出、关键链路跑通、AI 接入不因前期粗糙而推倒重来。Phase 1 进一步细化为三个 Step——先打地基，再上风险最高的阅读器，最后引入 AI 辅助。

### 5.1 Phase 1 / Step 1（框架 + 书籍管理：地基层）

把工程骨架、数据模型、存储、鉴权、文件管理、书架 CRUD、导出备份、部署全部就位；各模块入口预留，后续直接填充、不动地基。

- 工程骨架：pnpm monorepo（apps/web、apps/api、packages/shared、packages/db）；Fastify 后端 + Vite/React/shadcn 前端壳（套现有设计稿暖色主题）；Docker + docker-compose 一键起；Drizzle 迁移机制跑通。
- 数据模型与书架核心（对应 4.1）：全套表结构，`owner_id`/`visibility`/`deleted_at`/弹性字段从首日埋好；五状态体系（`存` 独立路径）+ 状态时间轴；元数据最小必填（书名+作者）；书籍 CRUD/详情/列表/搜索/筛选/排序/分页/批量；分类/标签/评分/可见性/阅读目的；回收站；规则版重复检测。
- 文件管理（对应 4.1 文件部分）：上传 EPUB/非 EPUB，支持 `local_only`/`cloud_only`/`dual` 三态存储策略；一书多文件、主阅读文件标记、列表/下载/替换/删除关联、类型标识、EPUB 封面抽取缓存；设置页批量上传弹窗可逐项覆盖存储方式。
- 导出与备份（对应 4.4）：元数据 JSON/CSV；笔记/高亮导出接口预留空实现；文件下载、手动全量备份 ZIP；SQLite 自动备份（VACUUM INTO 留 N 份）。
- 部署与鉴权（对应 4.5）：自托管 Docker、单账户登录、OPDS 1.2（KOReader 实测兼容）、概览首页核心（总数/状态分布/最近新增；最近阅读、高亮/笔记数量占位）。
- 入口预留：书籍详情页"阅读"按钮灰置 + 引导、"阅读痕迹"区空状态占位；侧边栏"主题""AI"导航占位；设置页"AI 接入配置""OSS 同步"表单入口可填但功能后置。
- Step 1 交付物：一个能完整管理书库、上传下载文件、导出备份、OPDS 订阅、单账户登录的自托管应用——除"打开阅读"外，书架能力全部可用。

### 5.2 Phase 1 / Step 2（引入阅读器：沉淀层核心）

进场前提：Step 1 的数据层、文件端点、鉴权、详情页入口已就位。本 Step 只碰技术风险最集中的阅读器，不再动地基。

- epub.js 集成：打开主 EPUB、目录、翻页。
- CFI 进度保存/恢复。
- 高亮/划线（CFI 范围 + 原文兜底锚点）、附注增删改、点击查看。
- 独立笔记（TipTap 富文本，可导出 Markdown）。
- 跳回原文（笔记/高亮 → 阅读器定位）。
- 标记体系（重要/疑问/启发，预留扩展）。
- 单书阅读痕迹汇总（激活 Step 1 预留占位）；笔记全文搜索（FTS5，复用 Step 1 检索层）。
- 详情页"阅读"按钮由灰置转为可用。
- 不做：阅读器增强项 3.21–3.31，仍预留待《决策记录》定位。

### 5.3 Phase 1 / Step 3（AI 阶段一：管理 + 阅读辅助）

进场前提：Step 2 已产出高亮/笔记，AI 阅读辅助才有原料。由原"Phase 1 前置"调整为 Step 2 之后。

- 录入辅助（9.01–9.04）、阅读辅助（9.05–9.08），直接调外部 LLM。
- 结果带引用（书 + 章节，9.16），存为 AI 派生资产并与用户内容隔离（9.14/9.15）。
- 无新基础设施；`AIService` 接口落地。

### 5.4 Phase 2（组织层 + AI 检索）

- 主题阅读（对应 4.3）、AI 阶段二 RAG 书库级（9.13/9.09–9.12/9.17）、概览统计核心激活。

### 5.5 Phase 3（增强与深化）

- AI 阶段三分级访问（9.18）、云同步 OSS、rclone / Google Drive / Dropbox 可选、阅读器增强项（待《决策记录》定位后）、阅读统计增强（待定位）。

增强层功能（阅读器 3.21–3.31、统计 5.09–5.17）须在《决策记录》确认定位后排期，技术路线上预留接口不提前实现。
