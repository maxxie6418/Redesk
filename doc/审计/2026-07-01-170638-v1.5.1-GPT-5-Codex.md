# Redesk 第一阶段审计报告

- 日期：2026-07-01 17:06:38
- 代码版本：v1.5.1
- AI 名称：GPT-5 Codex
- 审计范围：书籍新增、文件上传/匹配、存储策略、备份、账号与安全、概览与设置相关前后端实现
- 审计方式：静态代码审查 + 文档对照 + 本地类型/语法检查

## 验证结果

- `apps/api` 类型检查通过。
- `apps/web` 类型检查失败，当前工作区存在语法错误：`apps/web/src/routes/settings.tsx:1710-1717`。
- ESLint 失败，主因同样来自 `apps/web/src/routes/settings.tsx:1699` 附近的解析错误；另有 2 个 `react-refresh/only-export-components` 警告，位于 `apps/web/src/components/theme-provider.tsx:33`、`apps/web/src/components/ui/button.tsx:46`。

## 一、确认存在的问题

### P0

1. `dual` 存储模式并没有真正写入“双份”，当前只会写一个主存储。
证据：
- `apps/api/src/lib/storage-factory.ts:149-160` 将 `dual` 直接解析为主位置 `local`，实际驱动也只取本地存储。
- `apps/api/src/routes/files.ts:417-429` 上传时只调用一次 `storage.putStream(...)`。
- `apps/api/src/routes/files.ts:429-443` 对 `dual` 只记录 `local_path`，`remote_key` 实际为空，`sync_status` 却直接写成 `synced`。
影响：
- UI 和数据模型都在表达“本地 + 云端双存”，但真实行为不是双存。
- 一旦用户按这个心智依赖对象存储做冗余，会得到错误的安全预期。

2. 当前工作区前端已经无法通过类型检查，设置页存在语法级断裂。
证据：
- `apps/web/src/routes/settings.tsx:1710-1717`
- `apps/web/src/routes/settings.tsx:1699`
影响：
- 这不是风格问题，而是当前 web 端构建/类型检查直接失败。
- 在这个状态下继续堆功能，会掩盖更多真实问题。

### P1

3. 书籍写入链路没有校验 `category_id` / `genre_category_id` / `tag_ids` 的 `owner` 和 `type` 边界。
证据：
- `apps/api/src/routes/books.ts:372-405`
- `apps/api/src/routes/books.ts:427-438`
- `apps/api/src/routes/books.ts:1216-1233`
- `apps/api/src/routes/books.ts:1341-1373`
影响：
- 允许把不属于当前用户的分类或标签挂到自己的书上。
- 允许把 `GENRE` 写到 `category_id`，或把 `PERSONAL` 写到 `genre_category_id`，破坏双分类语义。

4. “设置/系统管理员”仍然被硬编码到 `owner_id = 1` / `user_id = 1`，和“已覆盖账号管理、多用户预留”不一致。
证据：
- `apps/api/src/routes/settings.ts:9-18`
- `apps/api/src/routes/settings.ts:24-72`
- `apps/api/src/lib/storage-factory.ts:9-21`
- `apps/api/src/routes/system.ts:155-179`
- `apps/api/src/routes/system.ts:279-287`
影响：
- 只要进入多用户或数据迁移场景，这块就会变成隐式系统账户依赖。
- 系统设置、存储配置、重置逻辑都绑定在“1 号用户”假设上，边界不稳。

5. 修改密码接口没有校验旧密码，只要求一个 `newPassword`。
证据：
- `packages/shared/src/schemas.ts:49-54`
- `apps/api/src/routes/auth.ts:201-218`
影响：
- 任何已持有会话的人都可以直接改密。
- 对“账号安全管理已基本覆盖”的说法不成立，至少缺少基础的二次确认。

6. “OSS 备份”并没有形成真正的备份闭环，当前只有对象存储接入和本地备份。
证据：
- `apps/api/src/routes/export.ts:203-226` 只做本地 `VACUUM INTO`
- `apps/api/src/routes/system.ts:198-215` 只做本地数据库备份
- 全仓库没有把备份文件上传到 S3/OSS 的实现调用，只有普通对象存储读写能力：`apps/api/src/lib/s3-storage.ts:61-218`
影响：
- 现在更准确的状态是“支持云端文件存储接入”，不是“备份已上云闭环”。
- 用户从产品角度会把“存储接入”和“备份可恢复”理解成同一层保障，这里存在预期落差。

### P2

7. 批量状态变更和单本状态变更的行为不一致。
证据：
- 单本自动补 `started_at` / `finished_at`：`apps/api/src/routes/books.ts:1239-1250`
- 批量 `set_status` 没有补齐：`apps/api/src/routes/books.ts:1320-1338`
影响：
- 相同业务操作因为入口不同得到不同数据。
- 后续如果做统计、排序或时间轴，结果会不稳定。

8. 概览页“收藏”指标仍是硬编码 `0`，不可信。
证据：
- `apps/web/src/routes/overview.tsx:154-160`
影响：
- 收藏功能已经存在，但概览 KPI 不接真实数据。
- 这会直接伤害用户对系统数据可靠性的判断。

9. 侧边栏长期显示“话题 = 0”，会把尚未进入当前阶段的能力伪装成坏掉的正式功能。
证据：
- `apps/web/src/hooks/use-sidebar-stats.ts:13-18`
影响：
- 对外表现像缺陷，不像占位。
- 在当前阶段更像噪音，不像有效导航。

## 二、从产品和使用角度看，当前还缺什么

1. 缺少“备份恢复”闭环。
- 现在有备份生成和列表，没有恢复入口、恢复确认、恢复前校验、恢复后回滚策略。
- 从用户视角，只有“能备份”还不算真正可用。

2. 缺少云端存储/备份的状态透明度。
- 当前有 `sync_status` 字段，但上传成功路径几乎都直接写成 `synced`。
- 没有重试任务、失败队列、手动补同步、最近一次同步结果、对象缺失校验。

3. 缺少“账号安全”最基本的操作保护。
- 改密不验旧密码。
- 系统重置只验 1 号管理员口令，角色边界仍偏脆弱。
- 没看到会话管理、设备登出、敏感操作二次确认这类基础能力。

4. 缺少“书库规模增长后仍可用”的列表策略。
- 书架前端仍主要靠大页加载，不是真正完成分页式使用体验。
- 文件库、概览指标也还有“当前页统计冒充全局统计”的风险点。

## 三、优化空间

1. 先收口“存储语义”，不要继续让文档、字段名和真实行为分叉。
- 如果 `dual` 还没做完，就不要把它标成可用完成态。
- 如果要保留，就需要补真实双写、补同步任务、补失败状态流转。

2. 把“系统级设置”从业务用户归属里剥离。
- 当前 `owner_id = 1` 是临时实现，不适合继续扩大覆盖面。
- 建议明确为真正的 system scope，或者明确限制当前阶段只支持单租户系统配置。

3. 给高风险链路补测试，而不是继续只靠手点。
- 优先级最高的是：上传/匹配/删除、存储模式切换、备份、认证、批量操作。
- 当前这几个模块的状态分支已经足够多，没有测试护栏会越来越难改。

4. 拆小几个已经过重的前端文件。
- `apps/web/src/routes/settings.tsx`
- `apps/web/src/routes/bookshelf.tsx`
- `apps/web/src/components/book-detail-sheet.tsx`
- 这些文件已经同时承载页面、状态、交互和业务分支，回归风险偏高。

## 结论

当前第一阶段不是“功能没做出来”，而是已经进入“主流程基本可走，但语义、边界和可靠性还没收口”的阶段。

如果按优先级排，建议先处理这 4 组问题：

1. 修复 `settings.tsx`，先恢复前端可校验状态。
2. 收口存储语义：明确 `dual` 与 OSS 备份到底哪些是真的，哪些还是占位。
3. 给书籍写入链路补 `owner/type` 校验，避免继续制造脏数据。
4. 补齐安全底线：改密验旧密码，清理 `owner_id = 1` / `user_id = 1` 的系统级硬编码。
