# Redesk v2.2.0 全流程体验审计

> 审计时间：2026-07-08
> 审计范围：从「发现一本书」到「沉淀为知识」再到「日常备份」的完整用户旅程
> 审计版本：v2.2.0
> 审计方法：逐环节走查代码实现，对照设计文档，从用户视角评估闭环程度与体验质量

---

## 一、审计背景

Redesk 定位为自托管的个人阅读管理与 AI 陪读系统。当前处于 M1 书架与文件管理已闭环、M2 阅读器部分实现的阶段。本次审计覆盖用户从录入书籍到阅读、标记、主题整理、备份导出的全流程，识别闭环断点和体验优化点。

---

## 二、全流程审计

### 第一站：发现并录入一本书

**用户场景**：在豆瓣上看到一本好书，想收入书架。

**当前体验**：
1. 书架页点击「添加书籍」→ 粘贴豆瓣链接 → 一键抓取元数据（书名、作者、出版社、简介、封面等自动回填） → 选择分类和标签 → 上传 epub 文件 → 保存
2. 也可以选择 CSV 批量导入一批书

**闭环程度**：✅ **基本闭环**。单本添加体验相当好——粘贴链接、抓取、补充、保存一气呵成。批量导入也支持。

**涉及实现**：
- 前端入口：`apps/web/src/routes/bookshelf/create-book-form.tsx`（CreateBookForm 组件）
- 元数据抓取：`apps/api/src/lib/book-metadata.ts`（POST /books/metadata/fetch）
- 文本解析兜底：`apps/web/src/routes/bookshelf/utils.ts`（parseDoubanMetadata）
- CSV 批量导入：`apps/web/src/components/batch-import-panel.tsx` + `POST /books/import`

**可优化点**：
- 添加书籍后缺少即时反馈路径。保存后书架列表刷新，但用户刚添加的书可能不在当前视图。保存成功后是否可以直接跳转到书籍详情页，让用户开始下一步操作（上传文件、开始阅读）？
- 缺少「先收藏后填详情」的轻量入口。有时只是在手机上看到一本书想快速记录，不想当场填所有信息。当前表单虽只有书名必填，但 UI 上字段很多，给人压力。可考虑一个「快速添加」模式（只输书名+作者），之后在数据维护中补充。

---

### 第二站：整理书籍属性

**用户场景**：书入库了，想补全信息。

**当前体验**：
1. 在书架找到书 → 点开详情页 → 档案 Tab → 编辑模式下逐字段内联编辑
2. 或者去设置 → 数据维护 → 批量筛选缺失项 → 逐本补充 / 批量抓取

**闭环程度**：✅ **闭环**。单本编辑和批量维护两条路径都有。

**涉及实现**：
- 书籍详情页：`apps/web/src/routes/book-detail.tsx` + `apps/web/src/components/book-detail-sheet/`
- 内联编辑组件：EditableTextField、EditableSelectField、EditableNumberField、EditableDateField、EditableLongTextField、EditableJsonField、EditableTagsField
- 数据维护 Tab：`apps/web/src/routes/settings/maintenance-tab.tsx`（861 行）
- 批量抓取：`apps/api/src/routes/books.ts` 中的 `/books/metadata/batch-preview` 和 `/books/metadata/batch-apply`

**可优化点**：
- 详情页编辑与数据维护的工作流割裂。在详情页能看到完整信息、能编辑，但不能批量操作。在数据维护能批量操作，但看不到封面、不能预览。两个场景之间没有跳转入口——在数据维护表格里点了书名，不能直接跳到详情页。
- 封面管理流程不够自然。添加书籍时如果同时上传了 epub，封面会自动抽取。但如果是手动添加的书没有文件，封面就是空白首字。用户得去详情页 → 选择封面 → 从源 URL 下载，操作路径较深。是否可以在数据维护中也显示封面缩略图，让无封面的书一目了然？

---

### 第三站：上传阅读文件

**用户场景**：书的元数据都填好了，现在要上传 epub 文件开始阅读。

**当前体验**：
1. 书籍详情页 → 文件列表 → 上传文件（支持 epub/pdf/mobi/txt/azw3/docx）
2. 或者在文件库页面独立上传，再通过智能匹配关联到书籍

**闭环程度**：✅ **闭环**。单本上传和批量匹配都有。

**涉及实现**：
- 文件上传：`POST /books/:id/files`（multipart/form-data）
- 文件库：`apps/web/src/routes/file-library/index.tsx`（FileLibraryPage）
- 智能匹配：`POST /files/match/candidates` + `POST /files/match/apply-batch`
- 存储工厂：`apps/api/src/lib/storage-factory.ts` + `apps/api/src/lib/s3-storage.ts`

**可优化点**：
- 文件上传后的下一步引导缺失。上传 epub 后，文件出现在列表里，但用户得手动关闭详情页、回到书架、找到那本书、再点「打开阅读」。上传完成后是否可以直接出现一个「开始阅读」按钮？
- epub 自动抽取封面的反馈不明显。上传 epub 后封面会被自动抽取，但用户可能没注意到。如果之前是空白封面，上传后封面突然变了，但没有任何提示告知「已自动提取封面」。
- 文件格式支持广泛但阅读器只支持 epub.js。上传了 pdf/mobi/txt 等格式的文件后，点「打开阅读」可能无法正常阅读。如果格式不支持，应该提前告知用户，而不是打开后才发现。

---

### 第四站：开始阅读

**用户场景**：打开 epub 开始阅读。

**当前体验**：
1. 书籍详情页 → 「打开阅读」→ 进入阅读器
2. 阅读进度自动保存（2 秒防抖），重新打开时恢复到上次位置
3. 可以做高亮、添加笔记、添加书签

**闭环程度**：⚠️ **部分闭环**。基础阅读和进度追踪已完成，高亮/笔记/书签的基础能力已实现，但深度功能不足。

**涉及实现**：
- 阅读器：`apps/web/src/routes/book-reader/`（epub.js 集成）
- 进度同步：`apps/web/src/routes/book-reader/reading-progress-sync.ts`（2 秒防抖，CFI+percentage 去重，连续失败警告）
- 进度 API：`apps/api/src/routes/reading-progress.ts`（GET/PUT /books/:id/reading-progress，GET /reading-progress/recent）

**可优化点**：
- TipTap 尚未集成。当前笔记是简单 textarea 纯文本编辑，技术方案中规划的 TipTap（HTML + Markdown 双存）尚未落地。`package.json` 中没有 `@tiptap` 依赖。`notes` 表预留了 `content_html` 和 `content_markdown` 字段，数据模型已就绪。
- 阅读器增强功能缺失。M5 规划中的主题切换、字体切换、专注模式、TTS、全文搜索等都未实现。对于长时间阅读场景，这些功能对体验影响较大。
- 阅读统计不够丰富。当前只追踪了进度百分比，缺少阅读时长、每日阅读量、阅读热力图等统计。M5 规划中有热力图和年度目标，但未实现。

---

### 第五站：标记（高亮 + 笔记 + 书签）

**用户场景**：阅读过程中，对重要段落做高亮标记、写下想法。

**当前体验**：
1. 在阅读器中选中文字 → 弹出操作气泡 → 高亮/添加笔记
2. 高亮和笔记自动关联到书籍和精确的 CFI 位置
3. 笔记支持纯文本，数据模型预留了 `content_html` 和 `content_markdown` 字段

**闭环程度**：⚠️ **基础闭环，但缺乏深度**。

**涉及实现**：
- 高亮 API：`apps/api/src/routes/highlights.ts`（CRUD + 按书籍/主题查询）
- 笔记 API：`apps/api/src/routes/notes.ts`（CRUD + 按书籍/主题查询）
- 书签 API：`apps/api/src/routes/bookmarks.ts`（CRUD）
- 阅读笔记页面：`apps/web/src/routes/reading-notes/`（时间线视图 + 导出）
- 加入话题对话框：`apps/web/src/components/add-to-topic-dialog.tsx`

**可优化点**：
- 笔记从阅读器到「阅读笔记」页面的流转不清晰。用户在阅读器里做的标记，在书籍详情页的「痕迹」Tab 能看到，在导航栏「阅读笔记」页面也能看到。但「阅读笔记」页面的功能定位不够明确——它是一个时间线视图？还是一个管理和二次加工的入口？
- 高亮/笔记缺乏回顾机制。标记做完后就沉没了。没有「今日标记回顾」、「间隔复习」等机制。对于学习型读者来说，标记的价值在于回顾和内化。
- 书签功能实现了但入口不明显。在阅读器里可以添加书签，但书签和高亮的区别、使用场景没有引导。

---

### 第六站：整理成主题笔记

**用户场景**：读了几本相关领域的书后，想把不同书中的观点整理成一个主题。

**当前体验**：
1. 导航栏 → 阅读主题 → 创建主题
2. 将书籍关联到主题（通过 `topic_books` 软引用）
3. 将不同书的高亮/笔记关联到主题（通过 `topic_highlights` / `topic_notes` 软引用）
4. 创建主题片段（`topic_segments`）组织章节结构
5. 添加沉淀内容（`topic_entries`）：问题、判断、比较三种类型
6. 时间线视图回顾主题的形成过程

**闭环程度**：✅ **结构设计完整，但实用深度不足**。

**涉及实现**：
- 主题后端：`apps/api/src/routes/topics.ts`（832 行，8 个中间表 CRUD + 时间线 + 沉淀）
- 主题前端：`apps/web/src/routes/reading-topics/`（列表视图 + 工作区视图）
- 主题 Hooks：`apps/web/src/hooks/use-topics.ts`（306 行，完整的 CRUD + 关联管理）
- 数据模型（6 张表）：topics / topic_books / topic_highlights / topic_notes / topic_segments / topic_entries
- 后端测试：`apps/api/src/routes/topics.test.ts`（535 行，12 个测试用例）

**可优化点**：
- 主题工作区缺少自由书写空间。当前只能添加结构化的「沉淀条目」（问题/判断/比较），但没有一个大的自由文本区域让用户写主题综述、读书笔记总结。一个主题阅读的最终产出应该是一篇综合性的笔记，而不只是碎片化的条目列表。
- 从阅读器到主题的路径不够顺畅。阅读时发现一个好段落想归入某个主题，需要：选中文字 → 高亮 → 加入话题 → 选择话题。这个流程可以接受，但「加入话题」的入口是否足够明显？
- 主题内的素材组织方式有限。`topic_segments` 和 `topic_entries` 提供了基本结构，但缺少拖拽排序、自由分组、看板视图等组织方式。当一个主题关联了几十条高亮和笔记时，如何有效组织？
- 主题缺少「导出为完整笔记」的能力。主题工作区积累的内容不能一键导出为一篇 Markdown 文档。这是「沉淀」环节的关键闭环——最终产出一篇可分享、可归档的笔记。

### 第七站：日常备份

**用户场景**：用了一段时间后，担心数据安全。

**当前体验**：
1. 设置 → 云备份 → 一键全量 ZIP 备份（DB + 文件 + Markdown 副本）
2. 手动触发 VACUUM 备份（SQLite 精简副本，保留 7 份）
3. 支持配置 S3/R2/OSS 云端存储

**闭环程度**：⚠️ **手动备份闭环，自动备份缺失**。

**涉及实现**：
- 全量备份：`POST /backup/full`（打包 DB + 存储文件 + Markdown 副本）
- VACUUM 备份：`POST /backup/trigger`（最多保留 7 份）
- 迁移前快照：`packages/db/src/preflight.ts`（`snapshotBefore()` + `preflight()`）
- 模块化备份服务：`apps/api/src/services/backup/`（13 个模块 + 5 个预设，后端已建，前端未接入）
- S3 存储：`apps/api/src/routes/storage.ts` + `apps/api/src/lib/s3-storage.ts`
- 备份设计文档：`doc/说明/备份系统设计说明.md`（1223 行）
- 备份恢复计划：`doc/todo/2026-07-06-备份恢复系统开发计划.md`

**可优化点**：
- 没有定时自动备份。用户得手动去点「全量备份」或「VACUUM 备份」。对于自托管应用来说，遗忘备份是最大的数据风险。应该有一个后台 cron 任务，每天自动执行 VACUUM 备份。
- 没有备份恢复功能。备份做了但不能恢复，等于半闭环。`backup/full` 生成了 ZIP，但没有对应的 `restore/full` 接口。用户拿到 ZIP 后不知道怎么用。
- 备份上传到云端未实现。S3 存储配置已有，但备份包不能自动上传到云端。用户得手动下载 ZIP 再上传。
- 模块化备份服务后端已建但前端未接入。13 个备份模块、5 个预设组合（system/books/notes/topics/full）都在后端就绪，但前端备份 Tab 还是简单的两个按钮。

### 第八站：数据导出（数据主权）

**用户场景**：想把数据导出到其他工具，或者做离线归档。

**当前体验**：
1. 书籍元数据导出（JSON/CSV）
2. 单书笔记/高亮导出（JSON/Markdown/CSV）
3. 全量 ZIP 备份

**闭环程度**：⚠️ **单书导出有，全量导出缺**。

**涉及实现**：
- 导出 API：`apps/api/src/routes/export.ts`（378 行）
- 导出按钮：设置页云备份 Tab + 阅读笔记页 ExportActions 组件
- 数据模型要求：决策记录要求「导出必须用通用格式（Markdown/JSON/CSV），不依赖 Redesk 专有结构」

**可优化点**：
- 缺少全量笔记/高亮导出。只能单本导出，不能一次性导出所有书的全部笔记和高亮。对于想迁移数据或做全量归档的用户来说很不方便。
- 缺少主题笔记导出。主题工作区积累的结构化内容（关联书籍、高亮、笔记、沉淀条目）不能导出。这是用户花最多心思整理的内容，应该有专门的导出路径。
- 外部笔记导入仅做了匹配识别，未实际写入。如果用户之前在其他工具（Notion、Obsidian）里有读书笔记，想迁移到 Redesk，当前做不到。`POST /import/notes` 仅识别匹配，注释标注「S2 激活」。

## 三、闭环断点总结

| 环节 | 断点 | 严重程度 |
|:---:|---|:---:|
| 录入 → 整理 | 添加书籍后无即时跳转到下一步的引导 | 🟡 |
| 整理 → 阅读 | 上传文件后无「开始阅读」引导 | 🟡 |
| 阅读 → 标记 | TipTap 未集成，笔记只能纯文本 | 🔴 |
| 标记 → 回顾 | 缺少标记回顾/复习机制 | 🟡 |
| 标记 → 主题 | 主题工作区缺少自由书写空间 | 🔴 |
| 主题 → 导出 | 主题内容不能导出为完整文档 | 🟡 |
| 使用 → 备份 | 没有定时自动备份 | 🔴 |
| 备份 → 恢复 | 没有备份恢复功能 | 🔴 |
| 数据主权 | 缺少全量笔记/主题导出 | 🟡 |

## 四、修改项清单

| 序号 | 环节 | 修改项 | 优先级 | 说明 |
|:---:|:---:|---|:---:|---|
| 1 | 备份 | 实现定时自动备份（容器内 cron） | 🔴 高 | 自托管应用的生命线，用户手动备份不可靠 |
| 2 | 备份 | 实现备份恢复功能（restore/full） | 🔴 高 | 备份做了不能恢复等于半闭环，已有开发计划文档 |
| 3 | 阅读/标记 | 集成 TipTap 笔记编辑器 | 🔴 高 | 当前纯文本笔记限制了表达力，数据模型已预留双存字段 |
| 4 | 主题 | 主题工作区增加自由书写区 | 🔴 高 | 从碎片标记到知识沉淀的关键跳跃 |
| 5 | 备份 | 备份包自动上传到云端（S3/R2/OSS） | 🟡 中 | S3 存储配置已有，备份上传需对接 |
| 6 | 备份 | 前端接入模块化备份服务 | 🟡 中 | 后端 13 个模块 + 5 个预设已就绪，前端未接入 |
| 7 | 导出 | 实现全量笔记/高亮导出 | 🟡 中 | 当前只能单本导出，数据主权要求全量可导出 |

| 9 | 导入 | 外部笔记导入实际写入（非仅匹配） | 🟡 中 | POST /import/notes 当前仅识别匹配，注释标注 S2 激活 |
| 10 | 录入 | 添加书籍保存后跳转到详情页 | 🟡 中 | 减少用户从「录入」到「下一步操作」的摩擦 |
| 11 | 录入 | 快速添加模式（只输书名+作者） | 🟡 中 | 降低录入门槛，适合移动端快速记录场景 |

| 17 | 阅读 | 不支持的文件格式提前提示 | 🟢 低 | 避免用户打开后才发现无法阅读 |
| 18 | 阅读 | 阅读器增强：主题/字体/专注/TTS/全文搜索 | 🟡 中 | M5 规划项，长期阅读场景的体验基础 |
