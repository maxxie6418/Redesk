# Redesk M1 审计报告

- 时间：2026-06-30 17:03:08
- 代码版本：v1.3.0
- 审计模型：GPT-5
- 审计范围：M1 书架、文件管理、概览、设置、导入导出相关前后端实现
- 审计方式：静态代码审计 + 文档对照 + 子代理并行交叉检查
- 验证限制：本次未完成 `pnpm typecheck` / `pnpm lint`。当前环境里 `pnpm` 会尝试重建根 `node_modules`，随后在 `D:\verySync\Git\Redesk\node_modules\.modules.yaml` 处触发 `EPERM`，因此本报告不把该结果当作代码结论

## 1. 根本逻辑有无问题

### P0

1. 分类/标签的 owner 与 type 边界没有守住。
   书籍创建、更新、批量更新时，`category_id`、`genre_category_id`、`tag_ids` 都是直接写入，没有校验这些 ID 是否属于当前用户，也没有校验分类 type 是否匹配字段语义。这会允许把别人的分类/标签挂到自己的书上，也允许把 `GENRE` 写进 `category_id`、把 `PERSONAL` 写进 `genre_category_id`，直接违反 `owner_id` 边界和双分类语义。
   证据：`apps/api/src/routes/books.ts:372-405`、`apps/api/src/routes/books.ts:427-438`、`apps/api/src/routes/books.ts:1222-1233`、`apps/api/src/routes/books.ts:1341-1373`

### P1

2. 错误归属一旦写入，读取侧还会把脏数据暴露出来。
   `serializeBooks` 在取标签时只按 `book_id` 关联，没有再按 `tags.owner_id` 过滤；如果前面已经写入了跨用户标签，这里会把别人的标签名直接返回给当前用户。
   证据：`apps/api/src/routes/books.ts:466-483`

3. 系统设置被硬编码绑在 `owner_id = 1`，和“预留多用户”设计冲突。
   鉴权模式和设置读取都固定读 1 号用户；删除用户接口又没有处理“该用户承载系统配置/业务数据”的情况。在 `foreign_keys = ON` 下，这会把“可删用户”变成运行期失败点，也让 1 号用户变成隐式系统账号。
   证据：`apps/api/src/routes/settings.ts:11-18`、`apps/api/src/routes/settings.ts:23-89`、`apps/api/src/lib/auth.ts:39-44`、`apps/api/src/routes/users.ts:107`、`packages/db/src/client.ts:18-20`

4. 标签筛选实现与 API 契约不一致。
   文档定义多个 `tag_id` 为 AND 关系，但实现使用 `inArray`，实际语义是 OR。用户一旦组合多个标签筛选，结果会比预期更宽。
   证据：`doc/API接口.md` 中标签筛选约定；实现见 `apps/api/src/routes/books.ts:530-560`

5. 重复检测的返回分数不是真实相似度，而且作者为空时会被高估。
   作者比较里直接使用 `includes`，空字符串会命中得到 `0.85`；最终返回的 `score` 也不是计算出来的标题/作者加权分，而是按重复个数拼的固定值。这和决策记录里定义的规则版重复检测不一致。
   证据：`doc/决策记录.md:204-205`、`apps/api/src/routes/books.ts:1556-1580`

6. 批量删除的 `affected` 返回值不可信。
   遇到 `STORED` 书籍时，后端只会删除可删子集，但响应里仍返回全部 `ownedIds.length`。调用方会误判“所有选中项都已成功删除”。
   证据：`apps/api/src/routes/books.ts:1398-1412`

### P2

7. 单本改状态和批量改状态行为不一致。
   单本 `PATCH /books/:id` 会在切换到 `READING` / `READ` 时自动补 `started_at` / `finished_at`；批量 `POST /books/batch` 的 `set_status` 不会。结果是同样的业务操作，因为入口不同而产生不同数据。
   证据：`apps/api/src/routes/books.ts:1240-1250`、`apps/api/src/routes/books.ts:1323-1338`

8. “最近阅读”目前不是“最近阅读”，而是“状态仍为在读且最近更新过”。
   这会把“改了一下元数据的在读书”算成最近阅读，和用户理解的“最近真的读过”不一致，也和文档状态标记发生冲突。
   证据：`apps/api/src/routes/overview.ts:39-45`、`apps/web/src/routes/overview.tsx:196-223`、`doc/Redesk-功能清单-v1.1.md:58`、`doc/Redesk-功能清单-v1.1.md:179`

## 2. 代码是否有优化空间

### 明确缺陷

1. 详情页“简介”编辑写错字段。
   `EditableField` 里没有 `description`，点击简介进入的却是 `customAttributes` 分支，保存时写入 `payload.custom_attributes`。这不是体验问题，是明确功能错误。
   证据：`apps/web/src/components/book-detail-sheet.tsx:99`、`apps/web/src/components/book-detail-sheet.tsx:161-192`、`apps/web/src/components/book-detail-sheet.tsx:1083-1098`

2. `custom_attributes` 的前后端类型已经漂移。
   后端返回的是对象，前端 `use-books` 却仍把它声明为 `string | null`；`BookDetailSheet` 又对它再次 `JSON.parse`，`BookEditForm`/`KeyValueEditor` 也按字符串流处理。这个区域现在很容易出现显示为空、编辑失败、值变成 `[object Object]` 等问题。
   证据：`apps/api/src/routes/books.ts:500-508`、`apps/web/src/hooks/use-books.ts:25`、`apps/web/src/components/book-detail-sheet.tsx:344-358`、`apps/web/src/components/book-edit-form.tsx:49-68`、`apps/web/src/components/key-value-editor.tsx:9-37`

3. 文件库顶部统计口径错误。
   “总数”用全量分页总数，“已关联 / 未关联 / 占用空间”却用当前页 50 条计算，页面语义会自相矛盾。
   证据：`apps/web/src/routes/file-library.tsx:84-89`、`apps/web/src/routes/file-library.tsx:104-140`

4. 概览页有看起来可用、实际无行为的按钮。
   “导入笔记”按钮没有 `onClick`，会形成伪入口。
   证据：`apps/web/src/routes/overview.tsx:160-164`

### 工程优化

5. 多处存在明显 N+1 查询。
   分类统计、标签统计、概览状态统计都在循环里单独 count。书架规模一大，设置页和概览页会先变慢。
   证据：`apps/api/src/routes/categories.ts:36-49`、`apps/api/src/routes/tags.ts:29-38`、`apps/api/src/routes/overview.ts:21-29`

6. 时间字段没有按仓库规则约束为 ISO 8601 UTC。
   `started_at` / `finished_at` 在 schema 里只是普通字符串，任何内容都能写入。后续排序、统计和导出都会建立在不可靠值上。
   证据：`packages/shared/src/schemas.ts:106-110`、`apps/api/src/routes/books.ts:1236-1238`

7. 前端关键页面组件过大，维护成本已经偏高。
   `bookshelf.tsx`、`book-detail-sheet.tsx` 都在单文件承载大量视图、状态、业务分支。继续打磨 M1 时，回归风险会越来越高。
   证据：`apps/web/src/routes/bookshelf.tsx`、`apps/web/src/components/book-detail-sheet.tsx`

8. 设置页没有复用统一壳层。
   目前它单独维护一套侧栏和主区布局，后续如果导航、统计或壳层交互变化，设置页很容易漂移。
   证据：`apps/web/src/routes/settings.tsx:102-139`

9. 当前几乎没有测试护栏。
   代码库里没有发现与 M1 相关的测试文件；对当前这种前后端状态已经开始分叉的阶段，这是明显风险。
   证据：本轮未检出测试文件；静态审计范围内未见 M1 测试目录/用例

## 3. 是否符合需求设定，从用户的角度看操作逻辑是否有优化空间

### 与需求设定不一致

1. M1 边界已经被前端实际突破。
   文档反复写“打开阅读仍灰置，M2 再进入阅读器”，但现在已经有真实 `/books/:id/read` 路由，详情页也可直接进入阅读器；与此同时，书架卡片又继续提示“阅读器将在 M2 上线”。同一能力在不同入口上出现互相矛盾的说法。
   证据：`doc/开发执行计划.md:76-92`、`apps/web/src/App.tsx:18-25`、`apps/web/src/components/book-detail-sheet.tsx:656-667`、`apps/web/src/routes/bookshelf.tsx:315`、`apps/web/src/routes/bookshelf.tsx:357`、`apps/web/src/routes/bookshelf.tsx:442`、`apps/web/src/routes/bookshelf.tsx:486`

2. 已宣称完成的功能和文档状态回填不一致。
   典型有三处：元数据预填契约已经从 `preview` 演化为 `fetch + apply`，但文档没有统一；`最近阅读` 页面已展示但功能清单仍标未开始；`导入外部笔记` 标已完成，但后端还只是识别与匹配占位。
   证据：`doc/API接口.md:163`、`apps/api/src/routes/books.ts:1072-1120`、`doc/Redesk-功能清单-v1.1.md:39`、`doc/Redesk-功能清单-v1.1.md:58`、`doc/Redesk-功能清单-v1.1.md:179`、`doc/Redesk-功能清单-v1.1.md:215`、`apps/api/src/routes/export.ts:235`

### 用户操作逻辑可优化点

3. 书架页实际上没有完成“支持分页”。
   现在前端固定请求 `page_size: 200`，没有真正翻页 UI。书多了以后，用户会以为系统只保存了前 200 条。
   证据：`apps/web/src/routes/bookshelf.tsx:1251-1260`

4. 书架筛选项来自“当前结果集”，不是完整分类/标签源。
   一旦先做过某次筛选，其他分类/标签选项会直接消失，用户没法稳定切换条件。
   证据：`apps/web/src/routes/bookshelf.tsx:1287-1294`

5. 概览页“最近动态”不能直达对象。
   用户点击最近动态里的书名，只会回到书架首页，不会进入该书详情，路径被打断。
   证据：`apps/web/src/routes/overview.tsx:183-189`

6. 文件匹配弹窗的搜索反馈偏弱。
   输入后点击放大镜只是把当前缓存结果复制到本地状态；如果查询尚未返回，面板就会空白，用户容易误以为“没有结果”。
   证据：`apps/web/src/routes/file-library.tsx:323-339`

7. 概览收藏数被硬编码成 0。
   收藏功能已完成，但概览 KPI 没接真实状态源，用户会直观感到“数据不可信”。
   证据：`doc/Redesk-功能清单-v1.1.md:68`、`apps/web/src/routes/overview.tsx:152-158`

8. 侧边栏长期展示“话题 = 0”会制造噪音。
   当前主题能力尚未进入 M1，继续把它作为正式统计项展示，只会增加“是不是坏了”的疑问。
   证据：`apps/web/src/hooks/use-sidebar-stats.ts:13-18`

## 结论

M1 现在不是“没做完”，而是已经进入第二类风险：功能主体大致齐了，但数据边界、文档契约、入口语义、前端状态源开始互相漂移。

如果按优先级收口，建议先处理这四组问题：

1. 分类/标签 owner 与 type 校验，避免继续制造脏数据。
2. 详情页简介编辑与 `custom_attributes` 类型漂移，先把当前明确错误修掉。
3. 统一 M1 边界叙述，决定“阅读器到底是灰置还是已开放”，然后同步文档与入口。
4. 修正书架分页、文件库统计、概览收藏/最近动态这些直接影响用户判断系统是否可信的入口。
